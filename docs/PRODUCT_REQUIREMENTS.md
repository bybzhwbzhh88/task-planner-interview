# 产品需求与规则

## 背景与问题

任务规划工具通过模型生成日程，额度决定用户能否继续使用，也代表产品需要承担的调用成本。现有流程缺少明确、可感知的扣额规则，可能出现余额不足仍调用、失败后仍扣额，以及并发请求超过余额等问题。用户也不清楚生成失败是否收费、失败后该怎么做。

## 目标

- 发起前展示剩余额度和本次成功生成的消耗。
- 额度不足时在服务端阻止请求，不调用模型。
- 用户只为成功生成并保存的日程承担 1 次额度消耗。
- 失败、处理中和成功状态有明确反馈及合理的下一步。
- 并发请求的额度扣减不超过可用余额。

## 核心规则

| 场景 | 额度结果 | 用户反馈 |
| --- | --- | --- |
| 生成并保存成功 | 净扣 1 次 | 展示日程及更新后的余额 |
| 发起时余额不足 | 不变，不调用模型 | 说明本次未生成；等待额度补充，若无入口则联系管理员 |
| 模型明确失败 | 净扣 0 次 | 说明未扣额度，建议检查任务后重试 |
| 生成处理中 | 最多暂时预留 1 次 | 显示处理中并阻止页面重复点击 |
| 并发请求 | 成功请求各消耗 1 次，累计不超过余额 | 各请求显示自己的最终状态 |

扣额的产品语义是“成功生成并保存后净消耗 1 次”。服务端可以先预留额度来防止并发透支，明确失败后必须释放预留；页面禁用按钮只是交互保护，不是额度正确性的保障。

## 范围与取舍

本次范围：单服务、单数据库、现有模拟模型、单次生成固定消耗 1 次、余额与结果状态反馈。

本次不做：充值/订阅、按 Token 计价、跨账号防刷、跨请求结果复用、崩溃后的自动补偿，以及生产级额度流水和审计。新账号初始 3 次额度沿用现状。没有现成充值入口时不展示虚构的购买按钮。

## 指标与观察

演示验收关注：余额不足调用模型数为 0；模型明确失败的净扣额为 0；成功保存数与净扣额相等；并发完成后的余额不小于 0。当前仓库没有线上埋点，以上通过服务端日志、日程记录和数据库余额核对，不将开发日志描述为线上分析能力。

## 主要风险

额度预留后进程崩溃，可能留下占用；生产方案需用带状态、幂等键和过期恢复的额度流水/生成任务处理。模型失败退款若自身失败，也必须作为系统异常暴露并可核对，不能伪装成普通失败。额度补充路径和客服责任需业务方进一步定义。
