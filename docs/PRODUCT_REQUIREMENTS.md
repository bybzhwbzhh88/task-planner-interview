# 任务规划工具额度处理优化 — 产品需求文档

 
**项目：** Task Planner Interview

## 1. 需求概览

### 1.1 问题判断

当前任务规划工具支持用户创建待办任务，并通过本地模拟 AI 生成日程。每个新账号初始拥有 3 个生成额度。

本次需求重点并非增加新功能，而是完善日程生成过程中的额度管理机制，解决额度扣减与生成结果不一致、额度不足时仍可能调用模型、并发请求造成额度透支，以及用户缺乏明确操作反馈等问题。

以上属于根据题目目标识别的待改进风险，不代表所有问题均已在运行环境中复现。

### 1.2 产品目标

- **额度准确：** 每次成功生成日程，仅消耗 1 个额度。
- **失败不扣费：** 模型明确返回失败时，不消耗额度。
- **防止透支：** 同一账号并发请求时，额度不得出现负数。
- **节约资源：** 额度不足时，不发起模型调用。
- **反馈清晰：** 用户能够理解生成结果、额度变化及下一步操作。

### 1.3 方案概述

采用“额度校验 → 原子预占 → AI 生成 → 成功确认 / 失败释放”的处理方案。

额度预占用于控制并发请求。只有成功生成日程，才最终确认消耗额度；明确失败则释放预占额度。

前端通过额度展示、加载状态、失败提示和按钮禁用提供操作反馈，服务端负责最终额度校验。

**当前完成状态：** 产品需求方案初稿；尚未修改代码，运行验证待执行。

## 2. 用户场景与需求

| 用户场景 | 用户需求 | 产品解决方案 |
|---|---|---|
| 正常生成 | 知道生成是否成功、消耗多少额度 | 成功后扣除 1 次并更新余额 |
| 额度不足 | 不希望发起无效操作 | 阻止调用并提示额度不足 |
| 生成失败 | 不希望因系统失败损失额度 | 释放预占额度并支持重试 |
| 连续点击 | 避免误操作造成重复消耗 | 生成期间禁用按钮 |
| 并发请求 | 多窗口操作时额度仍然准确 | 服务端原子预占额度 |
| 生成完成 | 了解下一步可以做什么 | 展示日程、剩余额度及后续操作 |

## 3. 核心业务规则

### BR-01 额度初始化

新用户注册后获得 3 个额度。

本次需求不增加额度购买、充值、订阅或自动恢复功能。

### BR-02 额度校验

用户点击“生成日程”时，服务端检查可用额度。

- 可用额度大于 0：尝试预占 1 个额度。
- 可用额度等于 0：拒绝请求，不调用模型。
- 额度检查与预占必须作为不可分割的操作执行。

前端按钮禁用仅作为交互优化，不替代服务端校验。

### BR-03 成功扣减

AI 明确返回成功且日程生成结果成功保存后，确认消耗本次预占的 1 个额度。

每个生成请求最多确认扣除 1 次，不得重复扣减。

### BR-04 失败处理

AI 明确返回失败时：

- 不确认消耗额度。
- 释放本次预占额度。
- 保留用户已输入的待办任务。
- 提示“生成失败，本次未消耗额度，请重试”。

若模型成功但结果保存失败，也应按未完成生成处理并释放预占额度。

### BR-05 并发控制

同一账号剩余 1 个可用额度时，若两个请求同时发起：

- 仅允许一个请求成功预占额度并调用模型。
- 另一个请求因无可用额度被拒绝，不调用模型。
- 成功请求完成后最终消耗 1 个额度。
- 失败请求释放额度后，用户可重新尝试生成。

不允许出现负额度，也不允许两个请求同时占用同一个额度。

### BR-06 请求重复与状态一致性

同一请求在处理过程中不得重复扣减或重复释放额度。

用户刷新页面后，额度应以服务端保存的最新状态为准。

模型超时、网络中断等结果不确定的情况，不应直接假定生成成功；需要由服务端明确请求最终状态，避免重复扣减。

## 4. 功能需求

| 编号 | 功能 | 具体要求 | 优先级 |
|---|---|---|---|
| FR-01 | 额度展示 | 显示当前可用额度 | P0 |
| FR-02 | 额度校验 | 无额度时阻止模型调用 | P0 |
| FR-03 | 额度预占 | 原子预占 1 个额度，避免并发透支 | P0 |
| FR-04 | 成功确认 | 成功生成并保存后确认消耗 1 次 | P0 |
| FR-05 | 失败释放 | 失败时释放额度并保留任务 | P0 |
| FR-06 | 操作反馈 | 展示生成中、成功、失败、额度不足状态 | P0 |
| FR-07 | 防重复点击 | 生成期间禁用当前页面生成按钮 | P1 |

## 5. 页面状态与交互规则

### 5.1 默认状态

- 展示当前可用额度。
- 用户添加待办任务后，可点击“生成日程”。
- 无额度时按钮不可用，并显示额度不足说明。

### 5.2 生成中

- 按钮显示“生成中…”。
- 禁止当前页面重复提交。
- 展示加载反馈。
- 页面额度展示应区分可用额度与处理中预占额度，避免用户误解。

### 5.3 生成成功

- 展示生成后的日程。
- 更新剩余额度。
- 显示“生成成功，已消耗 1 个额度”。

### 5.4 生成失败

- 保留待办任务。
- 释放预占额度并刷新额度显示。
- 显示“生成失败，未消耗额度，请重试”。
- 允许用户重新提交。

### 5.5 额度不足

- 禁止发起新的模型调用。
- 显示“生成额度已用完，暂时无法生成新日程”。
- 不展示当前产品尚不存在的充值或购买入口。

## 6. 异常场景及处理

| 异常场景 | 处理规则 |
|---|---|
| 额度为 0 | 拒绝请求，不调用模型 |
| 模型明确失败 | 释放预占额度，允许重试 |
| 多窗口并发请求 | 服务端原子预占，拒绝超额请求 |
| 用户连续点击 | 当前页面防重复提交，服务端独立校验 |
| 生成期间刷新页面 | 重新读取服务端额度和已保存结果 |
| 结果保存失败 | 不确认额度消耗，返回失败状态 |
| 网络中断或超时 | 显示结果待确认或请求失败，不盲目重复扣减 |

## 7. 范围与取舍

### 本期包含

- 额度校验与预占
- 成功扣减和失败释放
- 同账号并发控制
- 额度展示和操作反馈
- 异常场景处理

### 本期不包含

- 支付、充值、订阅
- 跨账号防刷
- 精确 Token 计价
- 跨服务分布式事务
- 服务崩溃后的自动补偿
- 跨请求生成结果复用

本期优先保证额度处理正确性，不扩展商业化能力。

## 9. 假设、风险与交接

**关键假设**

- 当前仅考虑单服务、单数据库环境。
- 模拟 AI 接口能够明确返回成功或失败。
- 每次生成请求独立计费，不跨请求复用结果。

**需要研发确认**

- 现有数据库如何记录预占与已消耗额度。
- 请求中断时如何识别及处理未完成的预占。
- 生成结果保存与额度确认如何保持一致。

**当前未完成事项**

- 核对现有代码的实际额度处理行为。
- 绘制完整业务流程图和关键交互原型。
- 将功能需求拆解为研发任务。
- 编写详细验收案例并记录验证结果。

**交接说明**

研发应优先实现服务端额度校验、原子预占及结果确认逻辑，再完善前端反馈。测试应重点验证模型调用日志、余额变化及并发请求结果，不能仅依据页面提示判断功能正确。
