## 改造前：缺陷复现

改造前 `generatePlan` 先调模型、最后才读 `context.user.credits` 判断，且读的是请求开始时的快照。
用同一个账号直接压接口，得到：

| 场景 | 预期 | 实测 |
| --- | --- | --- |
| 额度 0，发起 1 次 | 402，且不调模型 | HTTP 402，余额 0，但 `mock-ai.started` 增加 **1** 次 |
| 额度 1，并发 5 次 | 1 成功 4 拒绝，余额 0 | 5 次全部 **200**，余额 **-4**，`mock-ai.started` 增加 **5** 次 |

两条缺陷都被复现：额度不足时仍然产生了模型调用（白花钱），并发时额度被扣成负数。

## 改造后：逐条验收

命令：`node scripts/quota-check.mjs --log /home/wasp/wasp-git.log`，一次执行全部通过（PASS 21 项）。

| AC5 | 额度 3，并发 5 次 | 3 成功 2 个 402；余额 0；模型调用 3 次 | 状态码 `200,200,402,402,200`；余额 0；`started` 增量 3 | 通过 |

| AC8 | 三条类型/编译命令 | 均通过 | `wasp compile` 通过；两个 `tsc --noEmit` 均通过 | 通过 |

返回给前端的错误文案（取自实测响应）：

- 402：`额度不足：本次未调用模型，也未扣除额度`
- 502（模型失败且退补成功）：`生成失败：本次未扣除额度，可直接重试`
- 500（保存失败且退补成功）：`保存日程失败：本次未扣除额度，可直接重试`
- 500（退补也失败）：`生成失败，且额度状态待确认：请刷新页面查看剩余额度后再决定是否重试`

最后一条是"不确定就不承诺"的落点：退补失败时额度可能已经扣掉，此时再说"未扣除额度"就是假话（不变式 I4）。

AC2 与 AC7 分别验证两层：AC2 直接打接口，证明**服务端**拦得住（前端按钮禁用可以被 curl、开发者工具或另一个标签页绕过）；AC7 验证**页面**在额度为 0 时禁用按钮并给出下一步提示。两层都要有，缺一层要么体验差，要么能被绕过。

## AC7：页面表现（人工验证）

自动化脚本覆盖了接口层；页面层需要人点一遍，步骤如下：

1. 打开 `http://localhost:3000`，用验证脚本里的任一 `quota-*` 账号登录（密码 `pass12345`），或注册新账号。
2. 添加一条任务，点"生成日程" → 出现日程列表，下方"剩余额度"由 3 变成 2。
3. 再生成两次把额度用完 → "剩余额度：0 次"变红提示"额度已用完，本次不会调用模型；请联系管理员补充额度"，"生成日程"按钮置灰不可点。
4. 先成功生成一次并看到下方的日程；再添加一条描述含 `[fail]` 的任务，把额度补回到有余额的状态后点生成 → 弹出"生成失败"提示，文案含"本次未扣除额度，可直接重试"，"剩余额度"数字不变，**且下方上一次的日程消失**（不能把旧结果继续挂着冒充"本次日程"）。

实测结果（2026-10-22，Chrome 访问 `http://localhost:3000`）：

- 新注册账号额度 3，添加一条任务后生成一次 → 出现日程列表，"剩余额度"由 3 变为 2。
- 继续生成两次后额度归零："剩余额度：0 次"变红，提示"额度已用完，本次不会调用模型；请联系管理员补充额度"，"生成日程"按钮置灰不可点。
- 换新账号并添加一条含 `[fail]` 的任务后生成 → 弹出"生成失败"，文案为"生成失败：本次未扣除额度，可直接重试"，剩余额度仍为 3。

结论：通过。

### AC7b：失败后清空旧日程（人工验证）

`DemoAppPage.tsx` 在失败分支加了 `setResponse(null)`，行为变化是：失败后下方不再保留上一次成功的日程。步骤：

1. 新账号（额度 3），添加一条普通任务 → 点"生成日程" → 下方出现日程。
2. 再添加一条描述含 `[fail]` 的任务 → 点"生成日程"。
3. 预期：弹出"生成失败"、"剩余额度"仍为 2，**下方日程区消失**，页面不再显示"本次日程"标题。

实测结果（2026-10-22，Chrome 访问 `http://localhost:3000`）：

- 第一次生成成功，下方出现日程，"剩余额度"3 → 2。
- 添加含 `[fail]` 的任务后再生成 → 弹出"生成失败"，"剩余额度"仍为 **2**（额度未被扣）。
- 下方第一次生成的日程**已消失**，不再挂着旧结果冒充"本次日程"。

结论：通过。

> 顺带记录一个环境细节：本地跑双端口时，前端 3000 与 API 3001 都要能从浏览器访问，否则页面会报 `GET /auth/me` 网络错误。

## 未覆盖的部分

- **退补失败分支**：`quota.refund_failed` 这条路径只做了代码走查，没有在真实数据库上制造"预留成功、退补失败"的故障（要注入得改 Prisma 连接或加测试中间件，超出本轮范围）。因此它带来的文案变化（500「额度状态待确认」）未经实测，只保证该分支不会退化成"说了未扣但实际扣了"。
- **保存失败分支**：同上，只在代码层面存在对应 catch，未做故障注入。
- 崩溃窗口：预留成功后进程退出，额度少 1 且不退回。题面不要求，见 SPEC §8。
- 多标签页：额度以发起请求的页面为准，其他标签页不自动同步。
- 空任务：服务端不校验"至少一条任务"，直接调接口会用空任务生成并扣额度（沿用原有行为）。
- "用户被删除"与"额度为 0"都走 402（`updateMany` 返回 0 无法区分，见 SPEC §8 第 4 条），未做区分。
