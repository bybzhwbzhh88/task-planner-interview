# 额度处理产品方案

> 结论：把额度从“失败后才提示”改为“生成前可见、成功后扣除、失败不扣、并发不透支”的可预期机制。用户每次操作都能回答三个问题：现在有多少额度、这次要不要扣、如果失败怎么办。

## 1. 问题判断

日程生成是用户主动发起的单次付费动作。额度规则本身不复杂，但当前体验存在信息缺口和执行风险：

> 仓库没有原始流程图。当前行为的逐步还原和代码位置见 [FLOW.md](FLOW.md#0-现有流程及代码依据)。

1. 页面不显示余额，用户点击前不知道还能生成几次。
2. 余额为 0 时仍可能发起模型调用，最后才报错，用户等待了无意义的时间。
3. 失败提示没有说明是否扣费，用户无法判断是否应该重试。
4. 同一账号在多个标签页或快速重复操作时，可能出现额度被扣成负数，破坏账实一致。
5. 成功生成后没有“消耗了多少、还剩多少”的确认，用户需要自己猜。

这些问题的共同点不是文案，而是**额度状态没有成为生成流程的一部分**。因此方案优先保证状态可理解、结果可解释、并发可控，再考虑历史流水等增强能力。

## 2. 目标

### 用户目标

- 点击前知道当前余额和本次成本。
- 成功时明确知道扣了 1 个额度、还剩多少。
- 失败时明确知道没有扣费，并能直接重试。
- 额度不足时不用等待模型返回，立即得到原因和下一步。

### 业务目标

- 任何时刻同一账号的额度不为负。
- 只有真正拿到可查看日程的成功生成才计费。
- 额度不足时不产生模型调用成本。
- 用可观察的界面和事件记录降低客服解释成本。



## 3. 用户与场景

| 用户 | 场景 | 核心诉求 |
| --- | --- | --- |
| 新用户 | 首次进入，拥有 3 个额度 | 知道免费额度有多少，敢开始第一次生成 |
| 多次尝试的用户 | 已生成过几次，余额减少 | 知道每次成本，失败后不担心被误扣 |
| 多标签页用户 | 在两个页面同时点击生成 | 余额不被透支，后一个请求得到清楚解释 |
| 额度耗尽的用户 | 余额为 0 | 立即知道不能生成、本次没扣费、如何补充 |

| 编号 | 现状 | 用户影响 | 业务影响 | 优先级 |
| --- | --- | --- | --- | --- |
| P1 | 页面不显示余额 | 无法预判是否值得点击 | 首次使用信心低 | P0 |
| P2 | 额度不足仍会等待模型返回 | 无意义等待，误以为系统卡住 | 产生不必要的模型调用 | P0 |
| P3 | 失败提示不说明是否扣费 | 不敢重试，或重复点击 | 客诉和重复请求增加 | P0 |
| P4 | 并发请求可能一起通过 | 余额透支 | 账实不一致 | P0 |
| P5 | 成功没有成本和余额反馈 | 不知道剩余次数 | 使用深度不可解释 | P1 |

## 5. 产品规则

### R1 账户级额度

- 每个账号初始 3 个额度，额度为整数，按账号共享。
- 一次生成请求固定消耗 1 个额度，与任务数量、日程条目数无关。
- 本版本不定义额度过期规则。

### R2 成功才计费

- 服务端成功生成并保存可查看的日程，才允许最终扣除 1 个额度；结果保存与最终扣费必须同成同败。
- 模型明确返回失败、结果保存失败时，本次不扣额度；若已预留额度，必须释放。
- 请求超时或网络中断时，客户端可能不知道服务端是否已完成。此时按“结果待确认”处理，不能承诺未扣费；用户刷新后以服务端余额和日程记录为准。
- “不扣”在用户侧表现为余额不变；系统内部可以先占用再退回，但用户看到的最终结果必须一致。

### R3 余额不足不调用模型

- 余额为 0 时，生成动作不得进入模型调用。
- 用户应看到“额度不足，本次未生成，也未扣额度”，并知道下一步是联系管理员补充额度。
- 不使用排队等待，避免用户不知道请求何时会执行。

### R4 并发不透支

- 同一账号同时发起多个请求时，成功次数不得超过请求前的可用额度。
- 服务端必须在调用模型前原子预留 1 个额度；预留即计入可用余额，模型明确失败或保存失败时释放，成功保存后转为扣除。
- 超出额度的请求应快速失败，并说明“额度已被用完”，不得扣费。
- 额度不足或预留失败的请求不得调用模型。
- 已失败请求退回的额度，不会自动重试此前失败的请求；用户可以重新点击。

### R5 状态以服务端为准

- 页面在首次进入、手动刷新，以及生成得到确定结果（成功、模型失败、保存失败、额度不足、并发额度用完）后，都应读取服务端最新余额，不能把登录时的旧余额当作可用余额。
- 超时或网络中断进入“结果待确认”时，不自动刷新余额、不自动重试；只展示刷新入口，用户点击后再读取服务端最新余额与日程。
- 页面展示的余额是辅助信息，最终是否可生成、扣费多少以服务端返回为准。
- 多标签页显示可能短暂不一致，但不应导致负余额；用户下一次操作后应看到最新值。

### R6 成本透明

- 生成按钮附近固定展示“每次成功生成消耗 1 个额度，失败不扣”。
- 这里的“失败”指确定失败（模型明确失败、保存失败、额度不足等）；超时或网络中断按“结果待确认”处理，不承诺未扣费。
- 成功提示必须包含本次消耗和剩余额度。
- 不使用每次点击都弹确认框，避免为 1 个额度的动作增加多余摩擦。

### R7 登录与权限

- 任务规划页沿用现有登录能力，未登录或会话失效时跳转登录页，登录成功后回到任务规划页。
- 本版本没有独立权限申请、角色授权或浏览器权限弹窗；登录即代表可访问本人账号的任务与额度。

## 7. 状态、计费与文案

| 状态 | 进入条件 | 页面表现与固定文案 | 是否扣费 |
| --- | --- | --- | --- |
| 未登录 / 会话失效 | 未登录、登录过期 | 跳转登录页；提示“登录已失效，请重新登录”（首次进入不显示该提示） | 否 |
| 读取中 | 首次打开或刷新 | “额度读取中…”；生成按钮不可用 | 否 |
| 无任务 | 已登录且任务为空 | “请先添加待办事项”；生成按钮不可用 | 否 |
| 时长非法 | 工作时长不在 1–24 小时 | 行内提示“工作时长范围 1–24 小时”；生成按钮不可用 | 否 |
| 可生成 | 有任务、余额大于 0 | “剩余额度 N 次”；“每次成功生成消耗 1 个额度，失败不扣”；按钮“生成日程 · 消耗 1 额度” | 等待结果 |
| 生成中 | 已提交生成请求 | 按钮禁用并显示“生成中…”；任务与时长保持可见 | 等待结果 |
| 成功 | 日程已生成并保存 | 展示本次日程；“已消耗 1 个额度，剩余 N 个”；余额刷新 | 扣 1 |
| 模型失败 | 模型明确失败 | “生成失败，额度未扣除”；保留任务和时长；可重试 | 否 |
| 保存失败 | 模型成功但结果未保存 | “生成结果未保存，额度未扣除”；可重试 | 否 |
| 额度不足 | 余额为 0 | “额度不足”“本次未生成，也未扣除额度”“请联系管理员补充额度”；按钮不可用 | 否 |
| 并发额度用完 | 预留时已无可用额度 | “额度已被用完，本次未扣费”；余额刷新为 0 | 否 |
| 额度不可用 | 余额查询失败 | “额度暂不可用，请刷新”；生成按钮不可用，只保留刷新入口 | 否 |
| 结果待确认 | 请求超时或网络中断 | “结果待确认”“不自动重试，请刷新后查看余额和日程；如余额减少但无日程，联系管理员核对”；生成按钮不可用，只保留刷新入口 | 以服务端最终结果为准 |
| 中断后重新进入 | 生成中刷新、关闭或离开后再次进入 | 显示服务端最新余额和“上次生成结果未确认”；不自动重试、不恢复旧日程；余额大于 0 时可发起新请求，余额为 0 时按“额度不足”阻断 | 上次请求以服务端记录为准 |

## 8. 失败与扣费矩阵

| 场景 | 调用模型 | 最终扣费 | 用户下一步 |
| --- | --- | --- | --- |
| 无任务、时长非法、额度为 0 | 否 | 否 | 修正输入或联系管理员补充额度 |
| 并发预留失败 | 否 | 否 | 刷新余额；有额度后手动重试 |
| 模型明确失败 | 是，最多 1 次 | 否 | 修改任务后重试 |
| 结果保存失败 | 是，最多 1 次 | 否 | 直接重试；旧日程不得伪装成本次结果 |
| 成功保存 | 是，最多 1 次 | 是，扣 1 | 查看日程；可继续调整任务 |
| 超时或网络中断 | 可能已发起 | 未知，以服务端最终结果为准 | 刷新确认；不自动重试 |
| 登录失效 | 否 | 否 | 重新登录后返回任务规划页 |

## 9. 用户流程

主流程与页面状态见 [FLOW.md](FLOW.md)。核心原则是：余额可见 -> 请求中锁定按钮 -> 结果明确 -> 余额刷新。

## 10. 指标与事件

### 核心指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 负余额账号数 | `credits < 0` 的账号数 | 0 |
| 失败扣费率 | 未返回日程但余额减少的请求占比 | 0 |
| 无额度调用数 | 余额为 0 仍产生模型调用的次数 | 0 |
| 成功生成率 | 成功生成 / 有效生成点击 | 观察值，不做硬目标 |
| 失败后重试率 | 失败后 10 分钟内再次点击的会话占比 | 观察值，用于验证文案是否可行动 |

### 事件

| 事件 | 触发时机 | 关键字段 |
| --- | --- | --- |
| `quota_balance_viewed` | 页面读取到余额 | `available_credits` |
| `generate_clicked` | 用户点击生成 | `available_credits` |
| `generate_succeeded` | 返回可查看日程 | `credits_before`, `credits_after`, `duration_ms` |
| `generate_blocked_no_credit` | 因余额不足被阻止 | `available_credits` |
| `generate_failed` | 模型或保存失败 | `reason`, `credits_after` |
| `quota_refreshed` | 读取服务端最新余额 | `available_credits`, `trigger` |

事件只记录账号内部标识和额度数值，不记录任务正文，避免把用户待办内容写入分析系统。


## 11. 范围、假设与决策

### 本次范围

- 额度展示、生成前阻断、并发占用与释放、成功扣费、失败不扣费、余额刷新、多标签页一致性，以及相关登录/异常状态。
- 复用现有任务、时长输入和日程结果展示；不改变任务增删改查规则。



### 已定产品决策

| 决策 | 处理 |
| --- | --- |
| 0 额度、余额不可用或时长非法 | 生成按钮不可用，并在按钮附近说明原因；不得进入生成中，不得调用模型 |
| 补充额度后的刷新 | 管理员补充后，用户手动刷新或重新进入页面；不做自动轮询 |
| 超时或网络中断 | 显示“结果待确认”，不自动重试；刷新确认前生成按钮不可用，只保留刷新入口；刷新后以服务端余额和日程记录为准，不承诺未扣费 |
| 生成中刷新或离开 | 不自动重试，也不自动恢复上次结果；重新进入后显示最新余额和“上次生成结果未确认”；余额大于 0 时允许发起新请求，余额为 0 时按“额度不足”阻断 |
| 旧日程与新请求失败 | 保留旧日程，但明确标注“不是本次结果” |
| 登录与权限 | 登录是现有前置；无独立权限申请；会话失效回登录页 |
