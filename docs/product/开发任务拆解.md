# 额度处理：开发任务拆解

交接结论：先把生成资格、请求状态和成功结算统一到后台，再让页面按同一份状态反馈。额度不足的请求必须在模型调用前被拒绝；成功才扣次，明确失败只解除自己的占用。页面同时支持多个独立请求，并能查看仍展示的成功请求各自的日程。

状态：产品方向的研发交接说明，尚未进行方案代码实现。本文的“完成标准”是未来研发交付的判断依据，不表示软件已经满足。当前产品交付不以代码实现、`SPEC.md` 或实现后测试为完成条件。

## 建议实施顺序

先完成 D01 的统一状态及查询约定，D02、D03 据此处理生成资格与结算。D04、D05、D06 消费这些状态和结果；D07 为各项提供可核对的验证证据。前后端可以先对齐数据与错误含义，再分别推进，不需要先画更多页面。

职责为交接建议，不承诺人员安排。数据结构、接口形式、数据库并发保障和具体实现由研发选择；产品完成标准不能退化为仅禁用页面按钮。

## D01　统一请求身份、次数状态与结果查询

**目标：** 同一账号的多个请求各有自己的输入、占用、状态和结果；页面不会把不同时点的数字拼在一起，也不会拿另一份日程冒充本请求结果。

**具体行为：**

- 每个被接收的请求可被单独识别，记录其提交时的待办和时长，并能查询处理中、成功或明确失败的状态，以及本次是否已消耗次数。
- 每个请求只持有自己的占用。终态已经确认后，再收到完成通知只能读取既有结果，不能重复结算或改写成另一终态。
- 剩余次数 C、生成中占用 R、可用次数 A 由后台基于同一账号状态返回，附可比较的状态版本；正常状态满足 C ≥ R ≥ 0，A = C − R。
- 成功结果有稳定的服务端保存确认顺序、所属请求和可辨识信息。最近结果按该顺序确定，不按提交先后或浏览器响应先后确定。
- 所有状态和日程查询只返回当前登录账号的数据；不允许通过另一个请求标识读取其他账号结果。

**职责与依赖：** 后台负责状态、归属与查询约定；前端参与核对展示所需信息。D02—D06 依赖本项，具体存储设计不在本产品文档指定。

**完成标准：** 可分别查询多个独立请求，次数来自同一版本；重复完成通知、乱序响应和账号切换不串结果、不倒退状态。页面参照 02—08 的生成进度、最近成功日程，以及 12—15 的并发成功和指定结果。规则与案例对应见文末表格。

## D02　在模型调用前取得生成资格

**目标：** 次数不足或状态异常时，不发起模型调用；有余量时允许多个独立请求，不固定限制为三个。

**具体行为：**

- 先确认登录及输入有效，再用后台最新状态将资格检查和预留作为一个整体完成。只有正常状态且 A ≥ 1 才接收，接收后 R 增加一，C 不变，然后调用模型。
- 同账号并发请求不能同时取得同一份空余次数。仅前端判断、先读余额再分别处理，均不满足此要求。
- C = 0 返回次数已用完；C > 0 且 A = 0 返回次数正被占用；状态异常返回次数暂不能确认。拒绝时不占用、不调用模型、不扣次、不自动排队。
- 后台不信任旧页面展示的次数。已接收请求继续执行，新请求被拒绝不取消或释放其他请求。
- 已开始的请求使用其提交时的输入快照；之后编辑待办和时长只影响后续新请求。

**职责与依赖：** 后台负责资格与并发保障，前端负责输入提示及提前说明不可生成原因。依赖 D01；与 D03 对齐占用生命周期。

**完成标准：** 不足请求没有新增 `mock-ai.started`；最后一次只允许一个并发请求取得资格；可用次数足够时第四个独立请求也可接收。画板 01—03、06、11。

## D03　成功、明确失败和不确定结果分别结算

**目标：** 每份成功日程仅消耗一次，失败和拒绝不误扣、不多释放；用户得到的“成功”必须已可靠保存。

**具体行为：**

- 模型返回可展示结果后，保存本请求日程、确认成功、C 减少一和解除该请求占用一起生效。成功后可重新查询；不能只在浏览器内保存。
- 模型明确失败，不保存新的成功日程、不扣次，仅解除本请求占用，并保留其他请求状态。
- 结果保存与扣次明确整体回滚时，本请求不计成功、不扣次，释放本请求占用，反馈未保存成功、可以重试。
- 相同成功或失败通知重复到达时不再次扣次、释放或新增结果。被拒绝的请求没有占用，不能执行释放。
- 浏览器超时、断网或关闭不是明确失败，不据此释放后台占用或承诺未扣次；应查询本请求，按后台实际终态更新。崩溃自动补偿不在本项范围内。

**职责与依赖：** 后台负责整体确认和仅结算一次；前端使用本请求反馈，不依据账号余额差推断该请求是否扣次。依赖 D01、D02。

**完成标准：** 成功保存与扣次共同成立；明确失败和整体回滚不扣次；重复通知不改变已结算结果。画板 04—08、12。

## D04　按独立请求展示操作结果和下一步

**目标：** 用户知道是否开始、是否成功、本次有没有消耗，以及现在能做什么。

**具体行为：**

- 次数区突出当前可用，解释生成中占用与剩余，预留不能写成已扣次。未知次数不显示为零，旧响应不得覆盖较新状态。
- 仍有可用次数时允许继续提交另一份独立日程；没有可用次数时禁用新增生成并常驻说明。页面限制不替代 D02 的后台拒绝。
- 按请求分别显示生成中、成功、明确失败或待确认。成功说明本次使用一次；明确失败说明本次未消耗、保留输入、可修改后重试；待确认提供查询本请求入口。
- “本次未扣次”不等于账号余额没有变化，其他并发请求可以成功。失败不覆盖他人的状态，也不把旧日程称为本次新结果。
- 07“结果待确认”只有在最新次数已核对时才显示可信数字；若次数也未核对，使用 11 的未知表达。查询失败保留待确认，不能推断生成失败或自行释放占用。
- 已用完仍允许编辑待办、查看成功日程；全部被占用则提示等待处理结果后再看最新次数，不承诺完成后一定能再生成。不引导到不存在的充值或领取入口。

**职责与依赖：** 前端负责状态、按钮、文案及版本处理；后台提供 D01—D03 定义的真实状态。

**完成标准：** 用户能区分用完、占用、失败、结果未知和次数未知；各请求独立反馈，按钮与可执行下一步一致。画板 01—12。

## D05　刷新时恢复最近成功日程和真实处理状态

**目标：** 刷新不丢失已保存日程，不取消后台请求，不自动再生成。

**具体行为：**

- 进入或刷新页面时，读取当前账号最新次数、仍在处理的请求及最近成功日程；读取不调用生成模型、不扣次、不清零真实占用。
- 最近结果使用 D01 的服务端成功顺序，携带可辨识信息和生成时间，明确标为“最近一次成功日程”。次数用完不影响读取。
- 没有成功记录显示空态；日程读取失败只说明读取失败，提供重读入口，不推断生成失败、数据丢失或没有记录。
- 次数与日程读取分别处理。次数未知暂停新增生成，已成功读取的日程仍可看；仅日程读取失败且次数可信时，不把它当成额度不足。
- 切换账号时清除上一账号页面数据及正在查看的指定结果，忽略旧账号晚到的响应。

**职责与依赖：** 后台提供按账号过滤且稳定排序的读取能力；前端负责加载、空态、读取失败和账号切换。依赖 D01，与 D04 共用状态规则。

**完成标准：** 刷新后结果、次数和处理中请求与后台一致；空态、读取失败不误触发生成。画板 08—11。

## D06　从成功请求查看对应日程

**目标：** 两份独立请求都成功后，用户能分别查看两份已经消耗次数的结果，不仅能看到最后一份。

**具体行为：**

- 仍展示的成功请求旁提供“查看日程”，按该请求读取自身成功结果，不把它变成再次生成。处理中或失败请求不提供成功日程入口。
- 主任务页默认显示最近成功日程。点击“查看日程”打开弹层，展示该请求的生成序号、输入时长和保存时间；关闭弹层返回任务页。
- 查看、重新读取和关闭弹层不改变次数、输入、请求终态或最近成功排序，不调用模型。查看较早结果不把它改成最近结果。
- 指定结果读取失败时保持所选请求身份，重试只重读同一请求，不拿另一份日程冒充读取成功。
- 正在查看指定结果时，其他请求成功可以更新后台最近记录，但不突然替换弹层中的指定结果；关闭弹层后任务页展示最新最近结果。页面刷新回到默认最近日程。
- 入口只针对仍展示的成功请求；不新增完整历史列表、分页、搜索或保留期限承诺。账号切换后遵守 D05 的清理与隔离规则。

**职责与依赖：** 前端负责入口、结果身份与关闭；后台负责按请求及账号读取正确成功结果。依赖 D01、D03、D05。

**完成标准：** 两份成功日程都能从各自请求打开弹层并关闭；不扣次、不生成、不改变最近顺序；失败重读不串结果。对应画板 12“并发请求均成功”、13“查看生成1日程”、14“查看生成2日程”、15“查看生成3日程”。13、14 演示两份并发结果各自查看，15 对应主线 06 的生成3。

## D07　准备可核对的验证证据并完成交接

**目标：** 未来实现能被重复检查，证据能对应请求和案例，而非只看页面提示。

**具体行为：**

- 依据[验收案例](验收案例.md)准备独立测试账号、明确初始次数及可控制的模型成功、失败和等待条件；不用真实体验账号反复消耗次数。
- 保留本次操作的请求标识、次数与占用前后状态、结果归属和模型调用证据。一次 `mock-ai.started` 代表一次已发起模型接口调用，这一口径来自 [TASK.md](../../TASK.md)。
- 并发验收先让已接收请求保持处理中，再检查额外请求是否被拒绝，之后释放成功或失败；避免完成太快改变前置条件。
- 保存每条案例的操作、预期、实际结果及证据位置。未执行写未执行；原版实测、原型点击与新方案软件验收分开记录。
- 交接时核对规则、原型、状态文案、任务及案例的一致性，记录尚未完成事项和必要运行说明。

**职责与依赖：** 研发和验证人员在未来实现阶段准备验证条件与证据；产品核对行为与标准。贯穿 D01—D06，完成标准覆盖 A01—A31。
