# 日程生成额度处理方案

判断：额度检查发生在模型调用之后，既浪费调用，也无法可靠阻止同账号并发透支。方案：服务端在调用前原子占用额度，成功保存日程后结算，明确失败后释放；页面展示可用额度和具体下一步。当前状态：产品设计完成，尚未开发或进行应用运行验证。

## 1. 现状与目标

依据：[任务要求](../../TASK.md)、[服务端操作](../../src/demo-ai-app/operations.ts)、[页面](../../src/demo-ai-app/DemoAppPage.tsx)、[模拟接口](../../src/demo-ai-app/mockAi.ts)、[数据模型](../../schema.prisma)。

静态检查发现：服务端先调用模型，再用请求上下文里的 credits 判断能否扣费；扣费和结果写入已有事务，但并发请求仍可能同时通过旧余额判断。页面已有生成中的按钮禁用和额度不足提示，但未展示额度，失败提示缺少可操作说明。模拟失败通过抛出异常触发，不能只处理空结果。

目标是让用户回答三个问题：现在还能生成几次？这次是否扣了额度？接下来能做什么？发布门槛：所有 P0 验收案例通过，成功数与扣费数一致，额度不足时新增模型调用数为 0，并发期间可用额度始终不小于 0。

## 2. 范围与明确假设

- 延续新账号 3 额度、每份成功日程消耗 1 额度的规则。
- 单服务、单数据库；沿用本地模拟接口，不接真实模型。
- 不做充值、订阅、额度赠送或定期恢复；不显示无法兑现的“购买额度”“明天再试”。
- 不做跨请求结果复用、跨账号防刷、Token 计费及服务崩溃后的自动补偿。
- 不改变任务内容、优先级、日程算法或任务完成状态的原有含义。
- 产品决定：成功指模型返回有效日程且结果已保存、扣费已提交。仅模型返回成功而保存失败，不向用户宣告成功，不最终扣费。
- 产品决定：同账号可同时生成多份，只要每个请求都先获得独立额度。没有空闲额度时立即拒绝，不排队、不自动重试。不同请求各自成功，各扣 1 次。
- 假设用户可通过既有登录会话查询自己的额度与已保存日程；需要开发补齐页面入口，不新建复杂历史管理模块。

## 3. 额度规则（唯一规则来源）

| 编号 | 规则 | 可观察结果 |
|---|---|---|
| R1 | 服务端以当前持久化状态判断可用额度，不信任页面缓存或请求开始时的用户快照 | 页面显示旧余额也不能绕过限制 |
| R2 | 每次模型调用前，原子判断可用额度大于 0 并占用 1；只有占用成功才能调用 | 1 额度的两个并发请求最多启动 1 次模型调用 |
| R3 | 占用暂时减少可用额度，不等于最终消费；模型成功后，保存结果与最终结算不可部分成功 | 结果与扣费各发生一次；刷新可查看结果 |
| R4 | 模型明确失败时不保存新结果，释放本请求占用，且只能释放一次 | 额度回到请求前水平，可手动再试 |
| R5 | 没有可用额度时拒绝，不调用、不排队、不影响已有日程 | 可用 0，新增调用 0、新增结果 0 |
| R6 | 所有终态后刷新服务端额度；切回页面或主动点击“刷新状态”也刷新 | 跨页面操作后能看到最新额度；刷新本身不生成 |
| R7 | 网络断开或客户端超时不是服务端明确失败；不能直接宣称已退款 | 显示结果待确认，不自动发第二次生成请求 |

术语：剩余额度 B 为尚未最终消费的额度，处理中占用 H 为进行中的请求数，可用额度 A = B − H。必须满足 A ≥ 0、H ≥ 0。页面显示“可用 A 次 · 处理中 H 次”，辅助文字说明“每成功生成 1 次消耗 1 额度；处理中暂占额度，失败释放”。这些是业务语义，不强制对应三个数据库字段。

示例：初始 B=1、H=0、A=1；请求甲获准后 B=1、H=1、A=0；乙被拒且不调用。甲成功后 B=0、H=0、A=0；甲明确失败则 B=1、H=0、A=1。前端按钮禁用只是防误触，R2 才是防透支边界。

## 4. 异常与恢复边界

- 模型明确失败：保留任务、时长和上一份日程；刷新额度完成后允许手动重试。重试作为新请求重新获得额度。
- 模型成功但结果保存失败：服务端回滚未完成的结果与结算并释放占用；确认完成清理后提示“日程未保存，本次未扣额度，请重试”。清理状态未确认时按“结果待确认”处理。
- 客户端断网或超时：提示刷新额度及已保存日程，不展示未经确认的“未扣额度”。该页面暂不提供直接重试；刷新确认无进行中请求后，允许用户自行发起新的生成，并明确可能另消耗 1 额度。无需跨请求去重。
- 服务端崩溃、数据库持续不可用：显示状态无法确认；恢复后先查询。残留占用由开发人工核查，禁止前端自行加回额度；自动补偿不在本期范围。
- 新一轮失败或额度不足不清空上一份日程；上一份日程标注为“上次日程”，避免误认成本次成功。
