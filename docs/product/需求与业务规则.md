# 额度处理：需求与业务规则

当前判断：应在调用模型前，为每个生成请求取得一次额度的使用资格；请求成功保存后才实际消耗，明确失败则释放占用。允许同账号在额度支持的范围内并发，并在刷新后恢复最近一次成功日程。

状态：产品需求与业务规则已完成逻辑校核和边界补充，作为流程、原型及研发交接的依据。方案按扣除处理中占用后的可用次数允许并发，不设置固定三个并发上限，并纳入刷新恢复。本次交付产品需求、流程与原型、开发任务拆解和验收案例，未修改程序。各份材料统一引用本文件的规则编号；规则校核不代表改进后的软件已通过测试。

## 依据与范围

- [TASK.md](../../TASK.md) 规定：成功一次消耗一个额度；额度不足不调用模型；模型明确失败不扣；同账号并发不透支；用户知道结果与下一步。新账号初始三个额度也来自题目。
- 本期只考虑单服务、单数据库。不同请求可代表不同生成任务，不要求跨请求复用结果。
- 支付、订阅、跨账号防刷、精确 Token 计价、服务崩溃后的自动补偿不在必做范围内。仓库没有次数领取、充值或每日恢复的规则，不作相关承诺。
- 本期增加最近一次成功日程的恢复；不扩展成完整的历史版本管理。
- 下文的计数符号、处理策略和计算示例是本方案定义，不是招聘方另行规定的算法。

## 统一术语

| 名称 | 定义 |
| --- | --- |
| 待办事项 | 用户输入的一条待办。多条待办可以共同生成一份日程 |
| 一次生成请求 | 用户提交一组待办及可用时长，要求生成一份日程；这是本次额度规则的计量单位 |
| 剩余次数 C | 尚未因成功生成而消耗的次数，其中可能有部分正在被请求占用 |
| 生成中占用 R | 已被后台接收、尚未确认成功或失败的请求各自预留的次数 |
| 当前可用次数 A | 还能接收多少个新的生成请求，A = C - R |
| 最近一次成功日程 | 当前账号中，按服务端成功保存确认顺序确定的最新日程，不按请求发起顺序或浏览器收到响应的顺序确定 |

正常状态始终满足：C ≥ R ≥ 0，因此 A ≥ 0。当前页面显示的数字用于解释状态；后台最新状态决定是否接收请求。“剩余两次就允许两个并发”只适用于这两次尚未被其他生成请求占用的情况，不能忽略已有请求。

## R01：一次成功按整份日程计次

一份成功日程消耗一次额度，与其中包含多少条待办无关。不同请求分别处理、分别计算结果，不把其中一个请求的成功日程当作另一个请求的结果。

失败后由用户再次提交属于新的生成请求；它成功后才消耗一次。查看、刷新和恢复已保存日程都不消耗次数，不触发生成模型。

## R02：调用前检查并预留

后台确认登录、请求输入和待办满足生成前提，并确认额度状态符合 C ≥ R ≥ 0 后，使用账号最新状态检查 A。只有 A ≥ 1 才接收请求，并为该请求预留一次：R 增加一，C 不变，A 减少一，然后才调用模型。异常状态先按 R06 拒绝，不能靠异常数计算出的 A 取得资格。

“检查并预留”必须作为不可被同账号其他请求插入的整体处理。两个请求不能分别看到同一份空余次数后都通过。仅在页面判断或仅在调用前读取一次余额不足以满足要求。

请求被接收时确定本次待办与时长；之后的编辑不改变已开始的请求。每个请求可被识别，并能对应其处理状态与成功结果，以支持并发反馈和结果核对。具体数据结构由开发确定。

每个被接收的请求只持有自己的一份占用。被拒绝的请求没有占用，不允许执行释放操作。每份占用只能结算一次：请求从处理中进入成功或明确失败后，再次收到同一请求的完成通知，只读取已确认结果，不重复扣次或释放。独立的新请求仍按自己的资格处理，不要求跨请求复用结果。

## R03：按当前可用次数允许并发

只要 A ≥ 1，同账号就可以继续提交新的独立生成请求；已有一个请求在处理不构成统一拒绝理由。限制依据是该账号未被占用的次数，不设置固定的三个并发上限。

没有可用次数时，新请求直接拒绝，不调用模型、不消耗次数、不自动排队。正在处理的请求继续执行；用户根据它们的结果决定是否再次提交。

以下是规则计算示例，不是软件实测：

| 接收新请求前的状态 | 允许的行为 |
| --- | --- |
| C = 2，R = 0，A = 2 | 可以接收两个同时生成的请求 |
| C = 2，R = 2，A = 0 | 拒绝第三个请求，说明次数正被占用 |
| C = 3，R = 2，A = 1 | 还可以接收一个请求 |
| C = 1，R = 1，A = 0 | 拒绝额外请求，等待正在处理的请求确定结果 |
| C = 0，R = 0，A = 0 | 拒绝新请求，说明次数已用完 |

本期不额外承诺请求排队顺序或自动重试。前端可防止意外重复触发，但不能把不同生成请求一律合并，也不能代替后台资格检查。

## R04：什么算生成成功

本次模型返回可展示的日程，后台将该请求的结果保存，并完成一次扣次及对应占用解除，整体确认成功后，才将该请求记为成功。

仅模型返回成功不足以向用户确认成功；结果保存与扣次必须一起生效。成功后结果可被重新查询，不能只存在本次浏览器页面内。用户是否喜欢、采纳或完成日程不影响本次是否成功。

## R05：何时扣次

接收请求时只预留，不实际消耗。成功确认时，对仍处于处理中且持有占用的该请求一起完成：保存结果、C 减少一、R 减少一。该请求的成功状态也在这次整体确认中记录，之后不能重复扣次或再次解除占用。

成功不会额外释放一个可再次生成的次数，因为它的占用已经转换为实际消耗。例如 C = 2、R = 2 时，一个请求成功后变为 C = 1、R = 1，A 仍为零。

向用户说明“本次成功使用一次”，同时展示账号最新的可用次数与生成中情况；多个请求并发时，不保证账号余额仅比本次页面旧值少一次。

## R06：额度不足怎样拒绝

两种情况均发生在模型调用之前，但反馈需要区分：

- C = 0：次数已经用完。说明本次没有开始生成、没有额外扣次；用户仍可编辑待办、查看已保存日程。
- C > 0 且 A = 0：剩余次数都已被正在生成的请求占用。说明暂时不能新增生成，提示等待处理结果后查看最新次数，再决定是否继续。

不能只说“超过三个”，也不引导用户去不存在的充值、领取或账号处理入口。页面数据过期时，以后台判断为准，并更新显示。

如果发现剩余次数为负、占用为负或占用超过剩余次数，属于状态异常，不按正常额度继续计算和接收请求。新请求不调用模型、不扣次；提示暂时无法确认次数并提供重新读取状态的操作，查看已有日程仍可进行。历史异常数据的核查交给研发，不在产品规则中擅自清零或补发次数。

## R07：模型明确失败后怎样继续

后台确认仍处于处理中的本请求模型明确失败后，该请求不保存新的成功日程、不消耗次数，并仅解除自己的一次占用：R 减少一，仅就本请求而言 C 不变，因此腾出一次可用次数。重复处理同一失败结果不再释放占用，也不能释放其他请求的占用。

提示应说明“本次生成失败，未消耗次数”，保留待办，并允许用户修改后重试。上次成功日程继续保留，明确标注它是上次的结果。

其他并发请求独立处理；它们成功可能使账号余额减少，所以不能把“本次未扣次”写成“整个账号余额必定等于发起前”。当前模拟模型可通过待办中的 `[fail]` 触发明确失败；该触发方式用于验证，不作为产品操作说明展示给普通用户。

## R08：保存失败与结果不确定

如果模型已返回，但后台明确确认结果保存和扣次整体回滚，该请求不计成功、不扣次、解除占用，并告知用户未保存成功、可以重试。

浏览器断网、超时、关闭或刷新，不等于后台明确失败。不能因此直接提示“未扣次数”，也不能仅因前端等待结束就释放后台占用。后台实际确认成功或失败后，按对应规则结束处理。

结果尚不确定时，提示先查询该请求状态、账号最新次数和结果，再决定是否重试。仅看到“最近有一份成功日程”不足以判断哪个并发请求成功，状态与结果需要能够对应。本期不扩展服务崩溃后的自动补偿。

## R09：刷新后恢复最近一次成功日程

用户刷新或重新进入页面时，读取当前登录账号最近一次成功保存的日程，同时读取最新额度和仍在处理的请求状态。读取不会消耗次数，也不会自动发起新的模型调用。

- “最近”按服务端成功保存确认顺序确定；并发成功需要有稳定、可重复查询的先后依据，不能直接取未排序查询的第一条。
- 展示日程时携带可辨识的结果信息和生成时间，标为“最近一次成功日程”。它可能来自另一页面，不冒充本次页面刚刚发起的请求。
- 请求先发起但后完成时，按成功保存确认顺序更新。旧响应不能覆盖较新的成功结果；刷新与当前页面的排序依据应一致。
- 没有成功记录时显示尚无日程，不为填充页面而自动生成；读取失败时提供重新读取的操作，不把读取失败说成生成失败或数据已丢失。
- 即使次数已用完，仍可读取已保存结果。恢复只属于当前账号，退出或切换账号后清除上一账号的页面数据。
- 刷新时仍有生成中的请求，应继续显示其状态；刷新不取消它们，也不把对应占用清零。后续按后台确认结果更新次数和最近日程。

用户已确认：仍展示在生成进度中的成功请求旁提供“查看日程”。读取该请求对应的成功结果，用弹层标明生成序号、输入时长与保存时间；不能以账号最新一份结果代替另一请求的结果。页面默认区域仍展示最近一次成功日程。查看、重新读取该结果和关闭弹层均不消耗次数、不发起模型调用，也不改变输入、请求状态或成功排序。

查看指定结果时，如果其他请求随后成功，弹层继续展示用户正在看的指定结果；最近成功记录可在后台更新，关闭后任务页按最新状态显示。刷新或重新进入页面回到默认最近成功结果，不要求记住先前打开的弹层。结果读取失败时，针对同一请求提供重新读取，不切换为其他请求的结果、不提示重新生成。本期只为仍展示的成功请求提供查看入口，不新增完整历史列表、保留期限或分页。

## R10：反馈必须对应本次请求

每个生成请求都应让用户判断：是否被接收、是否成功、这一次是否消耗次数，以及下一步能做什么。新请求被拒绝或失败，不应覆盖其他请求的处理状态；日程区展示最近成功结果时，应与具体请求的成功/失败反馈区分。

前端呈现方式在后续页面状态设计中确定。页面可以区分“可用次数”和“生成中占用”，避免将占用解释为已经扣除；多个请求的响应先后不能使次数或结果倒退到旧状态。

剩余次数、生成中占用和当前可用次数应由后台基于同一份账号状态返回，并有可比较的状态版本。页面按较新版本更新，不能把不同时间的 C 和 R 拼接计算，也不能用晚到的旧版本覆盖新状态。尚未读取或读取失败时显示“次数状态待确认”，不能直接当作次数为零；生成资格仍由后台核对。

## 规则逻辑校核记录

本节是对产品规则的状态演算和边界走查，不是程序运行测试。数字与符号沿用本方案定义。

| 操作或边界 | 校核依据与结论 |
| --- | --- |
| 接收一个新请求 | 仅 A ≥ 1 时允许 R 增加一，因此仍有 C ≥ R，不能把同一可用次数分给多个请求 |
| 一个请求成功 | 该请求有占用，C 与 R 同时减少一，A 不变；占用转为消耗，不能再次用掉 |
| 一个请求明确失败 | 仅 R 减少一，A 增加一；释放该请求自己的资格，不消耗次数 |
| 同一完成通知被重复处理 | 已终结请求不再结算，避免重复扣次或重复释放造成虚假可用次数 |
| 次数用完、被占满或状态异常 | 均不接受新生成，不触发模型；拒绝原因和下一步分别说明 |
| 请求重叠、响应乱序 | 后台整体核对资格，额度按同一状态版本展示，日程按服务端成功顺序恢复 |
| 浏览器刷新或暂时断网 | 只读取真实状态，不额外调用模型、扣次或释放仍在处理的占用 |

在这些前提和题目限定的运行范围内，未发现本规则存在计数上的自相矛盾。代码实现是否满足规则属于研发与实现验收工作，不作为本次产品作业的完成条件。

本文件规定行为与边界。流程和原型按同一规则维护，新增按请求查看结果后，任务拆解与验收案例同步覆盖；软件验收仍待研发实现后执行。
