# 01 · 需求：日程生成的额度处理

## 1. 问题判断

现状不是「少了一个 `if`」，而是三件事被混在同一条时间里：**扣费时机、并发一致性、失败反馈**。

| 目标规则 | 现状行为 | 差距 |
|---|---|---|
| 每成功生成一次消耗 1 个额度 | 调用成功后才扣，事务内同时写结果 | 基本符合，但没有显式定义「成功」 |
| 额度不足时不应发起模型调用 | `generatePlan` 先调用模型（`operations.ts:49`），再判断额度（`:67`） | **违反**：额度为 0 时仍会产生一次 `mock-ai.started` |
| 模型失败时不消耗额度 | 事务在调用之后，异常时不会执行 | 结果符合，但属于「碰巧成立」，没有显式保证 |
| 并发请求不能透支 | 判断依据是 `context.user.credits`，即请求开始时的用户快照 | **违反**：两个并发请求读到同一个余额，都会通过检查 |
| 用户能理解结果并知道下一步 | 前端只区分 402 与通用错误，不显示余额 | **不满足**：用户不知道还剩几次，也不知道失败后额度有没有被扣 |

**结论**：需要把「检查额度」从调用之后挪到调用之前，并且从「读余额再判断」改成「条件更新」，同时补上前端的余额可见性与失败引导。

## 2. 范围

沿用 `TASK.md` 的范围：只考虑单服务、单数据库。不做支付、订阅、跨账号防刷、精确 Token 计价、崩溃后自动补偿。

本次改动只涉及「生成日程」这一条链路，以及它在页面上的呈现。

## 3. 规则定义与判定口径

| 编号 | 规则 | 判定口径 |
|---|---|---|
| R1 | 成功生成一次消耗 1 个额度 | 「成功」= 模型返回完整日程 **且** 结果落库成功。两步都完成才计费 |
| R2 | 额度不足时不发起模型调用 | 以「服务端拒绝」为准，不以「按钮是否可点」为准；接口被直接调用时同样不能穿透 |
| R3 | 模型明确返回失败时不消耗额度 | 「失败」含：接口报错、超时、返回结构不合法、返回空。超时按失败处理——用户没拿到结果就不该扣 |
| R4 | 同一账号并发请求不能透支 | 判定标准：任意并发组合下，`credits` 最终为 `初始值 - 成功次数`，且 `credits >= 0` |
| R5 | 用户能理解结果并知道下一步 | 每次操作后用户能回答三个问题：发生了什么、扣没扣额度、接下来能做什么 |

### R1 的边界

「生成成功但结果落库失败」按失败处理，额度退回。用户没拿到日程，就不算一次成功生成。

### R3 的边界

模型返回空日程（0 个任务）**不**算失败，算成功——用户确实没有待办，生成一份空日程是合理结果。但当前实现里「无任务」时按钮本来就不可点，这条只作为防御性定义。

## 4. 方案对比

| 方案 | 做法 | 能否阻止无限调用 | 并发是否透支 | 失败是否误扣 | 结论 |
|---|---|---|---|---|---|
| A 先查后扣 | 读余额 → 判断 → 调用 → 扣减 | 否（判断在调用前但非原子） | **会** | 否 | 现状，淘汰 |
| B 先扣后调 + 失败退还 | 条件扣减成功才调用；失败退还 | 能 | 不会（扣减是原子的） | 不误扣（有退还） | **选定** |
| C 成功后原子扣 | 调用成功后再条件扣减 | 否（额度不足仍会发起调用） | 不会 | 否 | 违背 R2，淘汰 |

**选 B 的理由**：只有「先占位」能在调用发生之前就把没有额度的请求挡掉；失败退还保证了 R3；扣减本身是单条带条件的更新，数据库层面天然串行，满足 R4。

**B 的代价**：请求期间额度被短暂占用；进程崩溃会导致额度丢失。后者明确不在本次范围（`TASK.md` 已排除崩溃补偿），在交接中记录。

## 5. 假设

| 编号 | 假设 | 如果不成立会怎样 |
|---|---|---|
| A1 | 部署为单实例，`credits` 只由本流程修改 | 若有其他入口扣减，需统一走同一套条件更新 |
| A2 | 数据库事务提供行级原子性 | 条件更新会退化为非原子，R4 失效 |
| A3 | 同一用户的请求量级很低（个位数并发） | 高并发下仍正确，只是失败请求会变多 |

## 7. 复现现状（给开发看）

> 以下三条已在原始代码上实际跑出结果（2026-10-26，WSL2 + Ubuntu 26.04 + PostgreSQL 18.6），实测数据见 `05-acceptance.md` §2.3。额度 0 时确实产生了一次 `mock-ai.started`；并发两请求后 `credits` 确实变成 `-1`。

三处问题都能在现有代码上直接观察到，不需要改代码：

1. **额度不足仍调用**：把测试账号 `credits` 置为 0，点「生成日程」。服务端日志出现 `mock-ai.started`，随后才返回 402。
2. **并发透支**：`credits = 1` 时同时发两个 `generatePlan` 请求。两个都通过 `context.user.credits > 0`，事务各扣 1，最终 `credits = -1`。
3. **失败无引导**：加一条含 `[fail]` 的任务后点生成。前端弹出通用错误，用户无法判断额度是否被扣。

操作方式见 `05-acceptance.md` 的 AC-00。
