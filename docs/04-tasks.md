## 2. 任务详情

### T-01 额度操作模块

**做什么**：把「扣」和「还」收敛成两个函数，调用方不直接写 Prisma 语句。

- `tryConsumeCredit(userId)`：执行一条带 `credits > 0` 条件的更新，返回是否扣到。
- `refundCredit(userId)`：`credits + 1`。

**验收标准**

- 余额为 0 时 `tryConsumeCredit` 返回 `false`，且不修改数据。
- 余额为 1 时并发调用两次，只有一次返回 `true`。
- 函数内不出现「先查询再判断」的写法。

### T-02 改造 generatePlan

**做什么**：把额度判断从调用之后挪到之前，并加失败退还。

顺序固定为：**参数校验 → 取任务 → 条件扣减 → 调用模型 → 落库 → 返回**。任一步失败，若已扣减则先退还再抛错。

**验收标准**

- 余额为 0 时，服务端日志**没有** `mock-ai.started`。
- 模型抛错时，`mock-ai.started` 存在、`mock-ai.failed` 存在，且请求结束后余额与请求前相同。
- 成功时余额减 1，`PlanResult` 新增一条。
- 并发两个请求、余额为 1 时，只有一个产生 `mock-ai.started`。

### T-03 错误码与文案

**做什么**：区分三类失败，让前端能分别处理。

| 场景 | HTTP 状态 | 前端行为 |
|---|---|---|
| 未登录 | 401 | 跳转登录 |
| 额度不足 | 402 | 提示 + 按钮置灰 |
| 模型失败 / 落库失败 | 424 | 提示 + 重试 |
| 参数不合法 | 400 | 提示参数问题 |

**验收标准**：三种失败在前端呈现不同文案，用户能看出「扣没扣额度」。

### T-04 余额查询

**做什么**：新增一个返回当前用户 `credits` 的查询，供页面展示。

**验收标准**：登录后页面能显示当前余额；生成成功/失败后刷新结果正确。

### T-05 前端余额与按钮态

**做什么**：按 `03-prototype.md` 实现「剩余 N 次」与按钮三态。

**验收标准**：余额为 0 时按钮置灰；生成中按钮禁用；余额随操作刷新。

### T-06 前端错误处理

**做什么**：按状态码分支提示，提供「重试」。

**验收标准**：402 与 424 显示不同文案，文案中包含「本次未消耗额度」的明确说明。

### T-07 验证

**做什么**：至少提供一份可重复执行的并发验证。

- 单元测试：用假存储模拟条件更新，验证「余额 1、并发 2 次只成功 1 次」。
- 端到端脚本：对运行中的服务并发发起 N 个 `generatePlan`，比对日志中的 `mock-ai.started` 数量与余额变化。

**验收标准**：两条命令可直接运行，输出可与预期对照（详见 `05-acceptance.md`）。

### T-08 文档同步

**做什么**：实现与本文档不一致时，先改文档再改代码；最终 `SUBMISSION.md` 的验证记录逐条对应验收案例。
