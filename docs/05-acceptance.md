# 05 · 验收案例

每条案例写成「前置 → 操作 → 预期」，预期都是**可从外部观察**的（日志、接口返回、页面、数据库值），不依赖读代码。

- AC-00 用于在**未修改的代码**上复现问题，证明诊断成立。
- AC-01 ~ AC-09 用于验收改后行为。
- 「规则」列对应 `01-requirements.md` 的 R1–R5。

## 0. 判定方式说明

| 符号 | 含义 |
|---|---|
| 日志 | 服务端控制台，关注 `mock-ai.started` / `mock-ai.succeeded` / `mock-ai.failed` 及其 `callId` |
| 余额 | 数据库 `User.credits`，或页面「剩余 N 次」 |
| 接口 | 直接调用 `generatePlan`（绕过页面），用于验证 R2「按钮置灰不能替代服务端拦截」 |

---

## AC-00 复现现状的三个问题（改前）

**前置**：原始代码，账号 `credits` 可控。

| # | 操作 | 现状预期（即缺陷） |
|---|---|---|
| 0.1 | 置 `credits = 0`，点「生成日程」 | 日志先出现 `mock-ai.started`，之后才返回 402 |
| 0.2 | 置 `credits = 1`，同时发两个 `generatePlan` | 两条请求都进入模型调用，`credits` 最终为 `-1` |
| 0.3 | 加一条 `[fail]` 任务后点生成 | 弹通用错误，页面无余额信息，无法判断是否被扣 |

**规则**：R2、R4、R5

> 0.1 的根因：`mockAi.ts` 在失败时抛 `Error` 而非返回 `null`，因此 `operations.ts` 里的 `generatedSchedule === null` 分支是死代码，错误会以 500 直接透出。

## AC-01 正常生成消耗 1 次额度

**前置**：`credits = 3`，有 2 条未完成任务。
**操作**：点「生成日程」。
**预期**：

- 页面展示日程，余额显示「剩余 2 次」
- 日志：`mock-ai.started` → `mock-ai.succeeded`，同一 `callId`
- 数据库：`credits = 2`，`PlanResult` 新增 1 条

**规则**：R1

---

## AC-02 额度为 0 时不发起模型调用

**前置**：`credits = 0`，有未完成任务。
**操作**：直接调用 `generatePlan` 接口（不经过页面，绕开按钮禁用）。
**预期**：

- 返回 402
- 日志中 `mock-ai.started` **数量为 0**（这是本案例的核心判据）
- 数据库：`credits` 仍为 0

**规则**：R2

---

## AC-03 模型失败不消耗额度

**前置**：`credits = 2`，任务中含一条以 `[fail]` 开头的任务。
**操作**：点「生成日程」。
**预期**：

- 返回 424，页面提示「生成失败，本次未消耗额度」
- 日志：`mock-ai.started` 与 `mock-ai.failed` 各 1 条
- 数据库：`credits` 仍为 2（扣了又退回，净变化 0）

**规则**：R3

---

## AC-04 落库失败不消耗额度

**前置**：`credits = 2`，人为让写入 `PlanResult` 失败（如临时断开数据库写入权限，或在测试中注入抛错）。
**操作**：点「生成日程」。
**预期**：

- 返回 424
- 数据库：`credits` 仍为 2

**规则**：R1（「成功」需模型返回 **且** 落库成功）

---

## AC-05 并发不透支（边界：余额 1，并发 2）

**前置**：`credits = 1`。
**操作**：同时发起 2 个 `generatePlan`（脚本或 `Promise.all`）。
**预期**：

- 恰好 1 个返回成功，1 个返回 402
- 日志中 `mock-ai.started` 恰好 1 条
- 数据库：`credits = 0`（**不是** -1）
- `PlanResult` 新增 1 条

**规则**：R4

---

## AC-06 并发不透支（放大：余额 2，并发 5）

**前置**：`credits = 2`。
**操作**：同时发起 5 个请求。
**预期**：

- 成功 2 个，402 三个
- `mock-ai.started` 恰好 2 条
- 数据库：`credits = 0`
- `PlanResult` 新增 2 条

**规则**：R4

---

## AC-07 并发中失败退还的净额正确

**前置**：`credits = 3`，5 个并发请求中含 2 个 `[fail]` 任务场景（或让其中 2 次调用注入失败）。
**操作**：同时发起。
**预期**：

- 净变化 = 成功次数（失败不计费）
- 最终 `credits = 3 - 成功次数`
- `credits >= 0`

**规则**：R3 + R4

---

## AC-08 余额可见

**前置**：`credits = 3`，进入页面。
**操作**：观察生成按钮附近。
**预期**：

- 常驻显示「剩余 3 次」
- 生成成功后立即更新为「剩余 2 次」，无需手动刷新页面

**规则**：R5

---

## AC-09 额度不足与失败的用户引导

| 子项 | 前置 | 操作 | 预期 |
|---|---|---|---|
| 9.1 | `credits = 0` | 进入页面 | 按钮置灰，「剩余 0 次」；点击无法发起请求 |
| 9.2 | `credits = 0` | 直接调接口 | 提示「额度已用完，本次未生成日程，也没有消耗额度」，并说明恢复方式 |
| 9.3 | 含 `[fail]` 任务 | 点生成 | 提示「生成失败，本次未消耗额度」，有「重试」按钮 |
| 9.4 | 9.3 之后 | 点「重试」 | 任务与时长仍在，不清空；重试不额外扣额度（若再失败） |

**规则**：R5

### 2.3 AC-00 实测结果（原始代码，2026-10-26）

请求通过 HTTP 直接打到 `POST /operations/generate-plan`，请求体为 superjson 格式 `{"json":{"hours":8}}`，鉴权用 `Authorization: Bearer <sessionId>`。额度用 `psql` 直接改 `User.credits`。

**AC-00.1 — 额度为 0，模型仍被调用**

- 前置：`credits = 0`，账号有 2 条未完成任务
- 操作：调用 `generate-plan`
- 实际：

  | 观察项 | 值 |
  |---|---|
  | HTTP | **402** |
  | 日志 | `mock-ai.started` + `mock-ai.succeeded`（同一 `callId`），共 **1** 次模型调用 |
  | `credits` 事后 | 0（未变） |

- **判定：缺陷成立**。402 是在模型返回**之后**才发出的，说明 `operations.ts:49` 的调用早于 `:67` 的额度判断。用户被拒绝，但服务端已经付出一次模型调用成本。

**AC-00.2 — `credits = 1` 时并发两个请求**

- 前置：`credits = 1`，2 条未完成任务
- 操作：两个 `generate-plan` 请求同时发出
- 实际：

  | 观察项 | 值 |
  |---|---|
  | 请求 1 / 请求 2 | **200 / 200**（都成功） |
  | `credits` 事后 | **-1** |
  | `mock-ai.started` | **2** 条 |

- **判定：缺陷成立**。两个请求读到的是同一个余额快照，都通过 `context.user.credits > 0`，各扣 1。这正是 R4 要防的透支，且余额已经变成负数。

**AC-00.3 — 模型明确失败时**

- 前置：`credits = 3`，任务中含一条 `[fail] 准备面试`
- 操作：调用 `generate-plan`
- 实际：

  | 观察项 | 值 |
  |---|---|
  | HTTP | **500** |
  | 响应体 | Express 默认 HTML 错误页，含 `Error: Mock provider explicitly rejected the request` 与源码堆栈 |
  | 日志 | `mock-ai.started` + `mock-ai.failed` |
  | `credits` 事后 | 3（未变） |

- **判定：部分成立**。额度「碰巧没被扣」——因为事务在模型调用之后，异常时根本没执行。但用户看到的是 500 堆栈页，无法判断额度状态，也不存在重试入口。同时印证了 `generatedSchedule === null` 分支是死代码：错误以异常形式穿透，走的是通用 500。

### 2.4 AC-01 ~ AC-07 实测结果（改后代码）

| 案例 | 前置 | 操作 | HTTP | 余额变化 | `PlanResult` | `mock-ai.started` | 结论 |
|---|---|---|---|---|---|---|---|
| AC-01 | `credits = 3` | 生成一次 | 200 | 3 → 2 | +1 | 1（started + succeeded） | 通过 |
| AC-02 | `credits = 0` | 直接调接口 | 402 | 0 → 0 | 0 | **0** | 通过 |
| AC-03 | `credits = 2`，含 `[fail]` 任务 | 生成一次 | 424 | 2 → 2（退还） | 0 | 1（started + failed） | 通过 |
| AC-04 | `credits = 2`，触发器模拟插入失败 | 生成一次 | 424 | 2 → 2 | 0 | 1（只有 started） | 通过 |
| AC-05 | `credits = 1` | 并发 2 | 1×200 / 1×402 | → 0 | +1 | 1 | 通过 |
| AC-06 | `credits = 2` | 并发 5 | 2×200 / 3×402 | → 0 | +2 | 2 | 通过 |
| AC-07 | `credits = 3`，含 `[fail]` 任务 | 并发 5 | 3×424 / 2×402 | → 3 | 0 | 3（failed 3） | 通过 |

**AC-02 是本次修复的核心判据**：额度为 0 时 `mock-ai.started` 为 **0**，模型一次都没被调到。改前同一场景是 1 条（见 2.3）。

**AC-07 验证退还在并发下也成立**：3 个请求扣了额度又各退回 1 次，另外 2 个在扣减处就被挡下拿 402，最终余额回到 3，全程未出现负数。

**AC-04 的模拟方式**：在 `PlanResult` 上装一个 `BEFORE INSERT` 触发器抛异常，让模型调用成功但落库失败。结果 424、余额不变、没有 `PlanResult` 新增，说明落库失败也走了退还分支。测完立即删除触发器。

**AC-01 顺带确认额度查询**：生成后 `get-my-credits` 返回 `{"json":2}`，与数据库 `credits = 2` 一致。
