# 开发任务拆解

| 优先级 | 任务 | 依赖/输入 | 完成定义 |
| --- | --- | --- | --- |
| P0 | 明确额度产品规则和异常文案 | 产品需求与流程 | 成功保存净扣 1；不足不调用；明确失败净扣 0；状态及下一步可理解 |
| P0 | 服务端额度原子预留 | 数据库条件更新、用户额度字段 | 仅余额大于 0 的一条并发请求可预留最后一次额度；余额不为负 |
| P0 | 模型调用及失败释放 | 模拟模型成功/失败行为 | 额度不足无模型调用；明确失败释放预留；失败释放异常可见且可核对 |
| P0 | 成功结果持久化及响应 | 日程结果存储 | 返回成功前结果已保存；成功后余额与净扣规则一致 |
| P0 | 页面余额和生成状态 | 服务端响应结构 | 展示余额、单次消耗、处理中、成功、失败、额度不足；处理中阻止重复点击 |
| P1 | 可重复并发验证 | 迁移后的 PostgreSQL、可运行应用 | 可设置余额并发请求，核对预留数、模型调用数、结果数和最终余额 |
| P1 | 验证交接 | Node/Wasp/PostgreSQL 环境 | 命令可重跑，记录通过项、未运行项和限制，不夸大验证结果 |

## 交付顺序

1. 确认扣额语义和失败边界，再实现服务端原子预留。
2. 覆盖额度不足、模型失败退款、结果保存及页面反馈。
3. 使用真实数据库执行并发脚本，核对模型调用数和最终余额。
4. 更新提交说明，区分静态检查、脚本验证和完整应用验证。

## 风险与后续

预留后崩溃、退款失败、客户端超时但服务端已完成等场景，需要生产级额度流水、幂等键、请求状态查询和过期恢复。本轮实现演示不覆盖这些机制；上线前应作为独立需求评估，而不是仅依赖按钮禁用或前端重试。
