# 额度处理验收案例

本文件定义产品方案的可观察验收标准。**所有用例当前均未在应用中执行**；应用尚未按方案实现。已完成的源码核查和文档检查见 [SUBMISSION.md](../SUBMISSION.md)。规则及开发任务以 [产品方案](PRODUCT.md) 为准。

独立原型的 10 项额度与任务交互检查、8 项主题专项检查单独记录在 [原型验证](../prototype/VALIDATION.md)，不计入本文件的真实应用验收。

## 准备与记录口径

- 按仓库 [README.md](../README.md) 启动应用。Windows 按其要求使用 WSL2、Linux 文件系统、Node.js 24.14.1+、Wasp 0.25.0 和独立 PostgreSQL 数据库；无需模型 API Key。
- 使用隔离测试账号，添加任务“整理面试资料”，工作时长设为 8 小时。修改初始额度前确保没有在途请求或残留预留；可使用 `wasp db studio`。不要改动其他账号或仅把前端显示改成目标值。
- `B/H/A` 分别为未消耗/预留/可用次数，定义见方案；`P` 为该账号已保存日程数，`C` 为本次测试窗口的 `mock-ai.started` 条数；预期以增量 `ΔP/ΔC` 表述。
- 记录该账号的请求标识及模型 `callId`，只计入其对应测试窗口。现有模型日志只有 `callId`，账号关联日志、请求状态和预留数据需开发补齐，当前不能假称已可直接查询。
- 每例记录执行时间、代码提交、前置数据、操作或命令、预期、实际、证据位置和结论。可用页面状态、接口响应、关联模型日志及数据库前后快照交叉核对；单看 HTTP 状态或按钮禁用不足以证明额度正确。

## 用例

存量迁移另设 M01，当前同样**未执行**：在隔离数据库准备余额为 2 和 -1 的旧账号，运行迁移预检，必须报告负余额并阻断上线，正常账号余额仍为 2。维护者依据该账号已有结果与调用记录完成核对、记录修正依据后再运行；迁移可完成，正常余额不变、所有初始预留为 0，满足 `0≤H≤B`。缺少核对依据时继续阻断，不能为了通过检查统一重置或把负值自动改为 0。此用例对应 D1，不代表已发现真实负余额账号。

## 并发验证应如何复跑

这是交给开发的验证规格，**不是已提供、已运行的脚本**。开发应在技术交付中给出一条可执行命令及实际输出。

1. 脚本使用已认证的独立测试账号，清理自身测试记录，确认无在途请求，设置 B=1、H=0，并保存基线 P 和日志位置。
2. 为模拟模型增加仅在测试中生效的屏障：第一个请求进入模型后先暂停，确保预留未释放。此时发送第二个生成请求，等待它收到准入拒绝，再放行第一个请求。两次按钮点击、两次顺序 `await` 或仅 `Promise.all` 都不能证明请求确实在预留期间重叠。
3. 分别执行 AC05 的成功和 AC06 的 `[fail]` 版本。核对响应、关联 `mock-ai.started` 数量、P 增量及最终 B/H/A；失败释放后再发一次请求，证明额度可以再次使用。
4. 每个版本用独立初始数据连续复跑 20 轮；任何一轮出现额外模型调用、负数、错误结果增量或残留预留，命令退出码必须非 0。
5. 再用 B=3、H=0 运行 AC07，证明方案允许有额度的不同请求并行，不把所有并发一律拒绝。两次成功必须对应两份结果和两次扣减。

测试屏障需在 `finally`/超时路径放行并清理，测试异常时结束该轮并报告，不能污染下一轮。故障注入及屏障不得默认启用，也不改变普通 `[fail]` 的行为。完整运行命令、测试数据准备及恢复步骤由开发一并提交。
