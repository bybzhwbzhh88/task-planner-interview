# 任务规划工具额度处理 — 验收测试案例

**关联文档：** PRODUCT_REQUIREMENTS.md、PRODUCT_FLOW.md、DEVELOPMENT_TASKS.md  
**验收状态：** 待执行

## 1. 验收目标

验证任务规划工具的额度管理逻辑是否满足产品需求，重点确保：

1. 成功生成日程时正确扣减额度。
2. 额度不足时不调用模型。
3. AI 生成失败时不消耗额度。
4. 同账号并发请求不会导致额度透支。
5. 页面正确反馈生成状态及剩余额度。
6. 异常情况下额度和生成结果保持一致。

## 2. 测试准备

### 2.1 测试环境

使用仓库现有任务规划工具及本地模拟 AI 接口。

测试人员需根据仓库 README 启动项目，并确认能够完成账号登录、添加任务及生成日程等基本操作。

### 2.2 测试数据

| 数据 | 说明 |
|---|---|
| Account-A | 新注册测试账号，初始额度 3 |
| Account-B | 用于账号隔离测试的独立账号 |
| Task-Normal | 普通待办任务，例如“完成项目报告” |
| Task-Fail | 包含 `[fail]` 的待办任务，用于模拟 AI 失败 |
| Task-Multiple | 包含多个普通待办事项的任务列表 |

说明：每个需要指定初始额度的测试用例，应使用独立测试账号或可重复执行的测试数据重置方式，避免前一个用例影响后续结果。

### 2.3 验证依据

测试时同时检查：

- 页面显示的剩余额度。
- 服务端保存的额度状态。
- 模型调用是否实际发生。
- 日程生成结果是否保存。
- 错误提示是否与实际结果一致。

不能仅依据页面提示判断测试通过。

## 4. 详细验收案例

### TC-01：新用户额度初始化

**关联需求：** BR-01  
**优先级：** P0

**前置条件：**

使用未注册过的新测试账号。

**操作步骤：**

1. 注册新账号。
2. 登录任务规划工具。
3. 查看页面显示的剩余额度。
4. 核对服务端额度数据。

**预期结果：**

- 新账号初始额度为 3。
- 页面与服务端额度一致。
- 未执行生成操作时不扣减额度。

**通过标准：** 初始额度准确且无异常扣减。

### TC-02：正常生成日程

**关联需求：** BR-03、FR-04  
**优先级：** P0

**前置条件：**

- 用户剩余额度为 3。
- 已添加普通待办任务。

**操作步骤：**

1. 查看当前额度为 3。
2. 点击“生成日程”。
3. 等待 AI 返回成功。
4. 查看生成结果和剩余额度。
5. 检查服务端模型调用记录。

**预期结果：**

- 成功生成并保存日程。
- 模型调用 1 次。
- 剩余额度从 3 变为 2。
- 页面提示生成成功。

**通过标准：** 生成成功且仅扣除 1 个额度。

### TC-03：最后一次额度使用

**关联需求：** BR-03  
**优先级：** P0

**前置条件：**

用户剩余 1 个额度。

**操作步骤：**

1. 添加普通待办任务。
2. 点击生成日程。
3. 等待生成成功。
4. 查看剩余额度。

**预期结果：**

- 日程生成成功。
- 额度从 1 变为 0。
- 生成按钮进入额度不足状态。
- 额度不出现负数。

**通过标准：** 最后一次额度可正常使用，成功后余额为 0。

### TC-04：额度不足时阻止调用

**关联需求：** BR-02、FR-02  
**优先级：** P0

**前置条件：**

用户剩余额度为 0。

**操作步骤：**

1. 进入任务规划页面。
2. 查看生成按钮状态。
3. 尝试通过正常页面操作生成。
4. 通过接口测试方式模拟直接提交生成请求。
5. 查看服务端模型调用记录。

**预期结果：**

- 页面提示额度不足。
- 正常生成按钮不可用。
- 服务端拒绝无额度请求。
- 模型调用次数不增加。
- 剩余额度仍为 0。

**通过标准：** 前后端均阻止无额度生成，且未调用模型。

### TC-05：AI 生成失败不扣额度

**关联需求：** BR-04、FR-05  
**优先级：** P0

**前置条件：**

- 用户剩余额度为 3。
- 待办任务包含 `[fail]` 标记。

**操作步骤：**

1. 添加带有 `[fail]` 的任务。
2. 点击生成日程。
3. 等待模拟 AI 返回失败。
4. 查看页面提示及剩余额度。
5. 检查服务端额度状态。

**预期结果：**

- 模型返回失败。
- 本次预占额度被释放。
- 最终剩余额度仍为 3。
- 原有待办任务不丢失。
- 页面允许用户重试。

**通过标准：** 明确失败不产生最终额度消耗。

### TC-06：失败后重试成功

**关联需求：** BR-04、FR-05  
**优先级：** P0

**前置条件：**

用户剩余额度为 3。

**操作步骤：**

1. 使用 `[fail]` 任务触发生成失败。
2. 确认剩余额度仍为 3。
3. 删除任务中的 `[fail]` 标记。
4. 再次点击生成。
5. 等待成功结果。

**预期结果：**

- 第一次失败不扣额度。
- 第二次成功扣除 1 个额度。
- 最终余额为 2。
- 用户能够看到成功生成的日程。

**通过标准：** 失败与成功请求独立结算额度。

### TC-07：同账号并发请求

**关联需求：** BR-05、FR-03  
**优先级：** P0

**前置条件：**

- 同一账号剩余 1 个额度。
- 准备两个浏览器窗口或并发请求工具。

**操作步骤：**

1. 两个窗口登录同一账号。
2. 分别添加普通任务。
3. 尽可能同时提交生成请求。
4. 等待请求结束。
5. 检查两个请求结果、额度及模型调用日志。

**预期结果：**

- 最多一个请求成功预占额度。
- 另一个请求因额度不足被拒绝。
- 最多发生 1 次模型调用。
- 若成功请求完成，最终余额为 0。
- 若成功预占的请求失败并释放额度，最终余额为 1。
- 不出现负额度。

**通过标准：** 并发竞争不导致额度透支或重复消耗。

### TC-08：连续快速点击生成

**关联需求：** FR-07  
**优先级：** P1

**前置条件：**

用户剩余额度为 3。

**操作步骤：**

1. 添加普通任务。
2. 连续快速点击“生成日程”按钮。
3. 观察按钮状态。
4. 查看模型调用记录和额度变化。

**预期结果：**

- 首次提交后按钮立即禁用。
- 当前页面不重复提交请求。
- 仅一次成功生成。
- 最终仅消耗 1 个额度。

**通过标准：** 连续点击不会产生重复请求或重复扣减。

### TC-09：刷新页面后额度一致

**关联需求：** BR-06、FR-01  
**优先级：** P1

**前置条件：**

用户已成功生成一次日程，剩余额度为 2。

**操作步骤：**

1. 查看当前额度。
2. 刷新浏览器页面。
3. 等待页面重新加载。
4. 检查额度及已保存的日程结果。

**预期结果：**

- 页面重新获取服务端额度。
- 剩余额度仍为 2。
- 已保存的日程结果不丢失。
- 不因刷新重复扣减额度。

**通过标准：** 页面状态与服务端持久化数据一致。

### TC-10：不同账号额度隔离

**关联需求：** BR-01、BR-02  
**优先级：** P0

**前置条件：**

Account-A 和 Account-B 初始额度均为 3。

**操作步骤：**

1. Account-A 成功生成一次日程。
2. 查看 Account-A 剩余额度。
3. 登录 Account-B。
4. 查看 Account-B 剩余额度。

**预期结果：**

- Account-A 剩余额度为 2。
- Account-B 剩余额度仍为 3。
- 不同账号额度互不影响。

**通过标准：** 额度与用户身份正确关联。

### TC-11：日程保存失败

**关联需求：** BR-04  
**优先级：** P1

**前置条件：**

- 用户剩余额度为 3。
- 测试环境能够模拟日程保存失败。

**操作步骤：**

1. 添加普通任务。
2. 发起生成请求。
3. 模拟 AI 返回成功。
4. 模拟日程保存失败。
5. 检查额度状态。

**预期结果：**

- 日程保存失败。
- 本次生成不视为最终成功。
- 预占额度被释放。
- 最终余额仍为 3。
- 页面提示生成未完成。

**通过标准：** 不出现日程未保存却消耗额度的情况。

**执行限制：** 若现有项目不支持模拟保存失败，应标记为“待环境支持”，不得直接记录为通过。

### TC-12：网络中断或请求超时

**关联需求：** BR-06  
**优先级：** P1

**前置条件：**

测试环境支持模拟网络中断或超时。

**操作步骤：**

1. 用户发起生成请求。
2. 在生成过程中模拟网络中断。
3. 重新连接并刷新页面。
4. 查询服务端请求状态及剩余额度。

**预期结果：**

- 不因网络中断自动重复扣减额度。
- 系统能够识别已完成或待确认的请求。
- 页面显示服务端实际状态。
- 不确定状态不被直接误判为成功。

**通过标准：** 不发生重复扣减，异常请求状态可追踪。

**执行限制：** 本期不强制要求服务崩溃后的自动补偿机制。

## 6. 验收通过标准

**P0 核心要求：**

- 成功生成只扣除 1 个额度。
- 额度不足时不调用模型。
- 模型明确失败不消耗额度。
- 同账号并发请求不透支。
- 不同账号额度互不影响。
- 核心操作具备明确用户反馈。

**P1 体验与异常要求：**

- 生成中禁止当前页面重复点击。
- 页面刷新后额度保持一致。
- 日程保存失败时不错误扣费。
- 网络异常不导致重复扣减。

最终是否通过验收，应依据实际执行结果，而不是仅依据文档设计。

## 7. 测试交接说明

建议研发及测试人员按以下顺序执行：

1. 验证正常生成与额度扣减。
2. 验证额度不足及模型调用阻断。
3. 使用 `[fail]` 验证失败释放。
4. 验证同账号并发请求。
5. 验证页面反馈及状态恢复。
6. 补充保存失败、网络异常等测试。

测试过程中应记录实际余额、模型调用次数、请求结果及相关日志，方便问题复现和后续修复。
