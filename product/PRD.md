## 0. 结论

**问题判断**：当前“生成日程”把额度判断放在模型调用之后，而且使用的是请求开始时的余额快照。结果是：额度为 0 的用户仍会触发一次模型调用；并发请求都认为余额充足时，可能把额度扣成负数。用户也看不到“这次扣了多少、失败有没有扣、余额为什么不够”。

**方案**：把额度当成一次“预扣—确认/退款”的资源占用。

1. 模型调用前，先原子预扣 1 个额度；没有额度就直接拒绝，不调用模型。
2. 模型成功且结果保存成功，预扣转为正式扣费。
3. 模型失败或结果保存失败，退回预扣，不扣费。
4. 页面始终展示真实余额，并用不同文案区分成功、额度不足、模型失败和参数错误。

**完成状态**：PRD、流程、可交互原型、任务拆解、验收案例已完成；原型覆盖 5 个演示场景，额度并发逻辑有可执行测试。真实后端/数据库不在产品方向内实现，工程落地要求见 [TASKS.md](TASKS.md) 的交接部分。

## 1. 背景与问题

用户添加待办任务后，可以按当天可用时长生成一份日程。新账号有 3 个额度，每成功生成一次消耗 1 个。额度是这个产品里唯一的“消耗型资源”，但当前流程存在四个体验/规则问题：

| 问题 | 用户感受 | 业务影响 |
| --- | --- | --- |
| 额度不足时仍发起模型调用 | 等待后才被告知不能用 | 浪费一次模型调用 |
| 并发请求使用旧余额判断 | 多开页面或快速点击后额度变负 | 额度透支，账实不符 |
| 模型失败没有明确说明“未扣额度” | 用户不知道要不要重试 | 不敢重试或重复点击 |
| 成功后余额不刷新、没有下一步提示 | 不知道这次扣了多少 | 对额度规则失去信任 |

本轮要解决的是**额度规则和用户理解**，不是支付、订阅或精确 Token 计价。

## 2. 目标与非目标

### 2.1 目标

- 额度不足时，不发起模型调用。
- 每次成功生成恰好消耗 1 个额度。
- 模型失败不消耗额度。
- 同一账号并发请求不透支。
- 用户在每个结果状态下都知道：发生了什么、扣没扣、还剩多少、下一步做什么。

### 2.2 非目标

- 支付、充值、订阅、发票。
- 跨账号防刷、风控、精确 Token 计价。
- 服务崩溃后的自动补偿、跨请求结果复用。
- 完整的历史记录、分享、导出。
- 多实例部署和分布式锁。

## 3. 用户与场景

| 用户 | 场景 | 关注点 |
| --- | --- | --- |
| 新用户 | 第一次生成日程 | 额度怎么用、这次扣多少 |
| 高频用户 | 一天内多次调整任务并生成 | 余额是否准确、并发是否安全 |
| 额度耗尽用户 | 生成时发现余额为 0 | 为什么不能用、怎么恢复 |
| 遇到失败的用户 | 模型返回失败或结果保存失败 | 有没有扣额度、能不能重试 |
| 管理员/演示者 | 本地调整额度、复现问题 | 规则是否可解释、证据是否可查 |

## 4. 规则定义

### 4.1 核心规则

| 编号 | 规则 | 用户可见结果 |
| --- | --- | --- |
| R1 | 新账号初始 3 个额度 | 顶部显示“剩余额度 3” |
| R2 | 每成功生成一次日程，消耗 1 个额度 | 成功提示写明“扣 1，剩余 N” |
| R3 | 额度不足时，不发起模型调用，也不扣额度 | 明确提示“未生成、未扣额度”，给出下一步 |
| R4 | 模型明确失败时，不消耗额度；如已预扣则退回 | 提示“失败，本次未扣额度，可重试” |
| R5 | 同一账号并发请求不能透支 | 最多 N 个请求成功，其余收到额度不足；余额不小于 0 |
| R6 | 余额以服务端为准 | 成功、失败、刷新后页面余额一致 |
| R7 | 无任务、时长非法时不调用模型、不扣额度 | 提示先添加任务或修正时长 |
| R8 | 每个被接受的请求代表一次独立生成 | 同一页面生成中禁止重复提交；多标签页分别计费 |

### 4.2 “成功”和“扣费”的口径

| 场景 | 是否算成功 | 是否扣费 | 用户看到 |
| --- | --- | --- | --- |
| 模型返回日程 + 结果保存成功 | 是 | 扣 1 | 日程 + 成功提示 + 剩余额度 |
| 模型返回日程 + 结果保存失败 | 否 | 不扣 | 失败提示，说明未扣额度，可重试 |
| 模型明确失败 | 否 | 不扣 | 失败提示，说明未扣额度，可重试 |
| 额度不足 | 否 | 不扣 | 额度不足提示，不发起生成 |
| 参数/任务校验失败 | 否 | 不扣 | 具体校验提示 |
| 网络异常、结果未知 | 未知 | 以服务端为准 | 提示刷新确认余额，不自动重试 |
| 用户成功后关闭页面 | 是（服务端已保存） | 扣 1 | 本轮无历史记录，属于已知限制 |

产品口径以“用户是否拿到可用日程且结果已保存”为准；不以“是否点击了按钮”为准。

### 4.3 并发口径

| 前置 | 并发请求 | 预期 |
| --- | --- | --- |
| 余额 1 | 3 个 | 恰好 1 个成功，2 个额度不足；最终余额 0；只发起 1 次模型调用 |
| 余额 3 | 5 个 | 恰好 3 个成功，2 个额度不足；最终余额 0；发起 3 次模型调用 |

实现上采用“模型调用前原子预扣”。预扣期间余额会暂时少 1；如果模型失败会退回。并发时后到的请求可能看到 0 而收到额度不足，即使先到的请求随后失败并退款。这是**保守但安全**的取舍：宁可让用户重试，也不透支或超发模型调用。

## 5. 用户流程

完整流程图、成功/不足/失败/并发时序见 [FLOW.md](FLOW.md)。

主流程：

```text
点击生成
→ 校验登录、任务、时长
→ 原子预扣 1 个额度
   ├─ 失败：额度不足，不调用模型，不扣费
   └─ 成功：调用模型
        ├─ 失败：退款，提示“未扣额度”，可重试
        └─ 成功：保存结果
             ├─ 保存失败：退款，提示“未扣额度”
             └─ 保存成功：展示日程，余额 -1，提示剩余额度
```

## 6. 状态、文案与下一步

文案原则：短、具体、不甩技术术语、不指责用户；每个异常都要回答“扣没扣”和“接下来做什么”。

| 状态 | 触发 | 页面呈现 | 主文案 | 下一步 |
| --- | --- | --- | --- | --- |
| 可生成 | 有任务、时长合法、余额 > 0 | 按钮可用，显示余额 | “每次成功生成扣 1 个额度” | 点击生成 |
| 生成中 | 请求已发出 | 按钮禁用，显示加载 | “正在生成日程，请稍候…” | 等待，不要重复点击 |
| 成功 | 模型和保存都成功 | 日程 + 成功横幅 + 余额更新 | “日程已生成。本次扣除 1 个额度，剩余 N 个。” | 可调整任务后再生成，会再扣 1 个 |
| 额度不足 | 余额为 0，或并发预扣失败 | 余额 0 高亮，生成按钮禁用/提示 | “额度不足：本次没有生成日程，也没有扣除额度。当前剩余 0 个。” | 联系管理员补充额度，或使用其他账号后再试 |
| 模型失败 | 模型明确失败，或结果保存失败 | 失败横幅，余额不变 | “生成失败：模型没有返回可用日程，本次未扣除额度。” | 删除含 `[fail]` 的任务，或稍后重试 |
| 无任务 | 任务列表为空 | 空状态 | “请先添加至少一个任务。” | 添加任务后再生成 |
| 时长非法 | 不在 1–24 小时 | 输入框提示 | “可用时长需在 1–24 小时之间。” | 修正时长 |
| 网络未知 | 请求超时/断网 | 黄色警示 | “网络异常，结果未知。请刷新页面确认剩余额度后再试，避免连续点击。” | 刷新确认，不自动重试 |

补充：

- 余额为 0 时，主按钮禁用，按钮附近常驻提示“额度已用完，本次不会发起生成，也不会扣额度”。服务端仍返回 402，作为并发和旧页面的兜底。
- 成功/失败提示优先用**页面内持久横幅**，toast 只作为补充；避免提示消失后用户不知道发生了什么。
- 不使用“扣费成功”这类容易误解为金钱的措辞，统一说“扣除 1 个额度”。

## 7. 页面与交互

| 区域 | 要求 |
| --- | --- |
| 顶部 | 始终显示“剩余额度 N”；0 时用警示色；成功后立即更新 |
| 任务区 | 支持添加/删除任务；空状态引导添加；保留任务时长 |
| 时长 | 1–24 小时，步长 0.5；前端校验，服务端再次校验 |
| 生成按钮 | 生成中禁用；无任务/0 额度时禁用；文案“生成日程”/“生成中…” |
| 结果区 | 成功展示日程；失败时清空本次结果并明确说明未生成，避免把旧日程误认为本次结果 |
| 提示区 | 成功/不足/失败用不同颜色和标题；移动端不被遮挡 |
| 无障碍 | 状态变化使用 `aria-live="polite"`；不只靠颜色区分；键盘可操作 |
| 响应式 | 桌面双栏，窄屏单栏；按钮和日志不横向溢出 |

产品原型见 [prototype/index.html](prototype/index.html)，无需安装依赖，直接打开即可。

## 8. 异常与边界

| 场景 | 期望行为 | 说明 |
| --- | --- | --- |
| 0 额度 + 含 `[fail]` 任务 | 先提示额度不足，不调用模型 | 额度检查优先于模型调用 |
| 无任务 + 0 额度 | 先提示添加任务 | 校验顺序：登录 → 任务 → 时长 → 额度 |
| 生成中重复点击 | 只发一次请求 | 按钮禁用；多标签页仍可能并发，由服务端额度兜底 |
| 成功后刷新 | 余额保持最新；最近日程可能不保留 | 本轮不做历史记录，列为已知限制 |
| 网络超时 | 提示结果未知，刷新确认 | 不自动重试，避免重复生成/重复扣费 |
| 管理员改额度 | 刷新后以服务端为准 | 本地演示用 `wasp db studio` 修改 |
| 退款失败 | 记录错误并返回失败；人工修正 | 崩溃补偿不在本轮范围 |
| 余额被手工改成负数 | 按 0 处理，不允许继续生成 | 服务端条件更新只允许 `credits > 0` |

## 9. 指标

产品上线后建议观察：

- 额度为负的账号数：应为 0。
- 0 额度时仍发起模型调用的次数：应为 0。
- 额度不足提示后，用户重试/联系管理员的比例。
- 同一账号短时间重复生成的成功率与重复扣费投诉数。
- 成功生成后余额展示与实际余额不一致的反馈数。

本地原型用“调用日志”验证：额度不足时不应出现 `mock-ai.started`；模型失败应出现 `started` + `failed`，且余额不变。

## 10. 决策与待确认

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| D1 | 结果保存失败不扣费 | 用户没有拿到可用结果，不应计费 |
| D2 | 0 额度时前端禁用按钮 + 常驻提示，服务端仍返回 402 | 提前阻止 + 并发兜底 |
| D3 | v1 不做幂等键 | 题目允许不同请求代表不同生成任务；先靠生成中禁用降低重复提交 |
| D4 | v1 不做历史记录 | 超出额度处理范围；列为已知限制 |
| D5 | 不做充值，额度不足引导联系管理员 | 当前是本地练习项目，无支付能力 |

待确认：

- 是否需要在下一版增加“最近一次生成结果”的持久化，避免成功后刷新丢失展示。
- 是否需要对多标签页/网络重试增加幂等键（同一请求只扣一次）。
- 额度不足时，除了联系管理员，是否提供“等待额度恢复”的说明。
