# 开发任务拆解

> 对应需求：[PRD.md](PRD.md) ｜ 验收：[acceptance.md](acceptance.md)
> 每个任务的"完成定义"都是**可观察的**，不写"保证并发安全"这类无法验收的句子。

## 1. 拆分原则

1. 一个任务 = 一个可以单独验收的切片。做完就能跑对应的验收案例，不必等整条链路通。
2. 顺序不可随意调：T1 之前没有任何东西能证明"额度不足不调用"，T6 的并发脚本必须等 T1+T3 落地才有意义。
3. 服务端先行，前端后接。前端不能用"置灰按钮"假装服务端安全。

## 3. 任务详情

### T1 · 预扣前置

- **目标**：额度不够的请求，在接触模型之前就被拦掉。
- **改动**：`generatePlan` 中取任务、校验参数之后，先读写额度；不足直接 `throw new HttpError(402, ...)`，此时**还没有** `generateMockSchedule` 调用。
- **完成定义**：
  - `wasp db studio` 把 `credits` 改为 0，点生成 → 服务端日志**没有**新的 `mock-ai.started`。
  - 响应状态码 402，页面停留原处，任务不丢。
- **注意**：这里只解决"顺序"，还不能解决并发。T1 单独上线时，并发仍可能透支——不要合并成一句"已修复额度问题"。

### T2 · 原子预扣

- **目标**：同一份余额只能被一个请求扣到。
- **做法（推荐）**：一条带条件的更新，用影响行数做裁决。

  ```ts
  // 伪代码：判断与扣减是同一条语句，中间没有时间窗口
  const { count } = await tx.user.updateMany({
    where: { id: userId, credits: { gt: 0 } },
    data: { credits: { decrement: 1 } },
  });
  if (count === 0) throw new HttpError(402, "No credits left");
  ```

- **不要这样做**：先 `findUnique` 读 `credits`，再 `update`。读写之间就是 D2 的窗口。
- **完成定义**：
  - 余额 1、三个并发请求 → 1 个 200、2 个 402；`credits = 0`，`PlanResult` 只 +1。
  - 余额 0 时任意并发，`credits` 始终 ≥ 0。
- **可选增强**：加 `CreditLedger` 流水表（`userId`、`delta`、`reason: reserve | consume | refund`、`callId`），用于崩溃后对账。加它会让 T3 的退款可追溯；不加也能满足本范围规则。**建议加**，成本一张表，收益是可交接。
- **关联验收**：AC-05、AC-06。

### T3 · 结算与退款

- **目标**：成功才消耗，失败退回。
- **做法**：
  - 预扣成功后调用模型；成功 → 写 `PlanResult` 并与"预扣转已消耗"放在同一事务。
  - 失败 → `credits + 1`（有流水表则追加一条 `refund`），不写 `PlanResult`。
  - `mockAi` 当前失败是 `throw Error`，不是返回 `null`。实现时用 `try/catch` 包住调用，并删掉 `=== null` 这段死代码（或统一改成返回 `null`，二者选一并写进注释）。
- **完成定义**：
  - 任务里含 `[fail]` → 生成失败，`credits` 与操作前相同，`PlanResult` 不新增。
  - 删除 `[fail]` 任务后重试 → 成功，`credits -1`（即 AC-08 的"3 → 失败 → 3 → 成功 → 2"）。
- **关联验收**：AC-03、AC-07、AC-08。

### T4 · 错误语义分类

- **目标**：用户能分清"没额度"和"生成失败"。
- **建议**：`402` 额度不足 / `502` 模型明确失败（可重试）/ `500` 其他异常（需排查）。前端按状态码分支，不靠字符串匹配。
- **完成定义**：三种情况各自触发不同 toast，文案见 PRD §6。
- **关联验收**：AC-02、AC-03。

### T5 · 前端额度可见

- **目标**：用户不必靠报错来推断余额。
- **改动**：在生成按钮上方常驻徽标 `剩余额度 N / 3 次`。数据来源必须是服务端返回值（生成 action 可返回剩余额度，或生成后重新查询），**不要**在前端 `3 - 已生成次数` 本地推算——运维改库后会对不上（假设 A2）。
- **完成定义**：
  - 页面加载即显示正确余额；生成成功后立刻更新。
  - 余额 0 时按钮置灰，悬停有说明。
  - 刷新页面，徽标与 `SELECT credits FROM "User" WHERE id=...` 一致。
- **关联验收**：AC-02、AC-12。

### T6 · 结果反馈三态

- **目标**：每次操作结束，用户知道"成了没有、扣没扣、还剩几次"。
- **改动**：
  - 成功 toast：`日程已生成 / 本次消耗 1 次额度，剩余 2 次`。
  - 失败 toast：`生成失败，本次未扣额度 / 剩余额度 2 次不变`，并清空"生成中"态。
  - 失败时旧日程保留，但上方加一行 `以下为上次成功生成的结果（14:20）`——直接对应 D5，不给用户误认的机会。
- **完成定义**：三条文案都有剩余次数或"未扣额度"字样；失败后屏幕上的日程不会被当成新结果。
- **关联验收**：AC-01、AC-03、AC-04。

### T7 · 防重复提交

- **目标**：连点两下不要变成两次扣费。
- **改动**：`isPlanGenerating` 已有，但状态更新是异步的，快速双击可能双发。用 `useRef` 加同步锁，请求开始置位、`finally` 复位。
- **完成定义**：快速双击生成按钮，服务端只出现 1 条 `mock-ai.started`。
- **关联验收**：AC-09。

### T8 · 并发验证脚本

- **目标**：让"不会透支"这句话可被任何人重复验证。
- **做法**：`scripts/verify-concurrency.mjs`，读取 `DATABASE_URL`，通过应用 action（或直接 HTTP）以同一账号并发 N 次，结束后查询并断言：
  - `credits >= 0`
  - `credits === 初始额度 - 成功次数`
  - 成功次数 ≤ 初始额度
  - 日志中 `mock-ai.started` 条数 === 成功次数
- **完成定义**：`node scripts/verify-concurrency.mjs --credits 1 --requests 3` 一条命令输出 PASS/FAIL 与关键数值；连续跑 10 次不出现负数。
- **关联验收**：AC-05、AC-06。技术方向可再把它包成 vitest 用例，本题不强制。

## 4. 依赖与建议节奏

```
T1 → T2 → T3 → T4 → T5 → T6 → T7
                    └→ T8（T3 完成即可并行开始）
```

T1-T3 是服务端正确性，做不完就等于没做；T5-T7 是体验，可以在服务端稳定后一次做完。

**如果只有一天**：只做 T1、T2、T4、T6 和 AC-01 / AC-02 / AC-05。这四项覆盖了题目四条硬规则中的三条（阈值、并发、可解释），并把"失败不扣额度"用现有 `throw` 路径挡住——但要在文档里明确写出"退款路径未实现，失败时靠预扣未发生来保证净消耗 0"，不能假装做完了。

## 5. 交接给下一位时需要确认的事

- 预扣是否落了流水表？没有的话，崩溃恢复只能靠人工比对 `PlanResult` 与 `credits`。
- 前端徽标的数据来源是服务端返回值还是二次查询？两者都行，但要一致，且刷新后仍正确。
- `mockAi` 的失败表达统一成 `throw` 还是 `null`？删掉另一种，避免下一个接手者再被死代码误导。
