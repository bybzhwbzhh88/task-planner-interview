# 需求方案：日程生成的额度处理

## 1. 问题判断

当前版本里，"额度"只是一个放在请求末尾的计数，没有作为一次生成任务的前置约束来对待。对照代码与目标规则，存在三个明确缺陷：

| # | 现状（代码位置） | 违反的规则 |
| --- | --- | --- |
| B1 | `generatePlan` 先调用 `generateMockSchedule()`，**之后**才在事务里判断 `credits > 0`（`src/demo-ai-app/operations.ts`） | 额度不足时不应发起模型调用——现在额度为 0 仍会打出 `mock-ai.started` 日志并等待 500ms |
| B2 | 额度判断读的是请求开始时的快照 `context.user.credits`，扣费与判断不是同一个原子操作 | 同一账号并发请求时，两个请求都读到 credits=1，都通过判断，都扣费，额度被打成 -1（透支） |
| B3 | 前端不展示剩余额度；额度不足 toast 文案为"请检查账号状态"，用户不知道下一步能做什么 | 用户需要理解操作结果，并知道接下来可以做什么 |

补充说明：模型失败路径目前是"歪打正着"——`generateMockSchedule` 遇到 `[fail]` 会直接 throw，异常冒泡后根本走不到扣费那一步，所以失败恰好没扣额度。但这是靠异常路径"碰巧"成立，不是设计出来的，需要在本方案里把它变成显式、可验证的行为。

## 2. 目标

让"额度"成为一次日程生成任务的完整生命周期约束：**扣得准（不多扣不少扣）、扣得安全（并发不透支）、扣得明白（用户全程知道额度和下一步）**。

### 2.1 核心业务规则（不可变）

1. 每**成功**生成一次日程，消耗 1 个额度。
2. 额度不足时，**不得发起**模型调用（不产生 `mock-ai.started`）。
3. 模型**明确返回失败**时，不消耗额度。
4. 同一账号**并发**发起请求时，额度不得被透支（剩余额度最低为 0，不得为负）。
5. 用户在任何一步都能理解发生了什么、以及接下来可以做什么。

### 2.2 范围与假设

- 只考虑单服务、单数据库。不做支付、订阅、跨账号防刷、精确 Token 计价、崩溃后自动补偿。
- 不同请求代表不同生成任务，不要求跨请求复用同一份结果。
- 一个新账号初始额度固定为 3，本需求不涉及充值/加额入口（见 §6 待办）。
- 模拟接口一次调用约 500ms；`[fail]` 任务用于制造"模型明确失败"。

## 3. 用户故事

- 作为一个新用户，我注册后有 3 次免费生成机会，我想清楚看到自己还剩几次，避免点了按钮才发现不能用。
- 作为用户，当我额度用完时，我希望立刻知道"我没有额度了、这次没有调用模型、不会扣我东西"，而不是转半天圈后报错。
- 作为用户，当模型失败时，我希望知道"这次没扣额度，我删掉出问题的任务后可以重试"。
- 作为用户，我连续快速点多次"生成日程"时，系统应该像排队一样只放进去我额度够的次数，不能偷偷把我额度扣成负数。

## 4. 功能需求

### F1. 额度前置校验与原子扣费（对应 B1、B2）

一次生成请求按以下顺序处理，"校验"与"扣费"必须在同一条数据库原子语句里完成：

1. 鉴权通过后，先原子地尝试扣 1 个额度：`UPDATE User SET credits = credits - 1 WHERE id = ? AND credits > 0`，并检查本次实际命中行数。
2. 命中 0 行（额度不足）→ **直接返回 402，不调用模型**，不产生 `mock-ai.started`。
3. 命中 1 行（额度已被预扣）→ 才调用 `generateMockSchedule`。
4. 模型成功 → 写入 `PlanResult`，请求结束（额度已扣，无需再动）。
5. 模型失败（含 `[fail]` 抛出）→ **回滚这 1 个额度**（`credits = credits + 1`），返回明确错误。

> 为什么是"先扣后退"而不是"先查后扣"：先查 `credits > 0` 再扣，两步之间没有锁，并发下必然超扣；把判断写进 `UPDATE ... WHERE credits > 0` 的条件里，数据库行锁天然把并发请求串行化，命中行数就是"是否拿到了额度"的唯一事实来源。这是 §4 防止透支的具体落点。

### F2. 模型失败不扣额度（对应现状的"歪打正着"）

- 模型失败时，除了回滚额度，返回给前端的错误要区分"模型失败（可重试、未扣额度）"和"额度不足（不可重试、需加额）"两种。
- 删除含 `[fail]` 的任务后，用户可立即再次生成。

### F3. 额度可见（对应 B3）

- 页面固定位置展示"剩余额度：X 次"，X 来自服务端实时值，而不是本地数出来。
- 成功生成后，展示"本次已消耗 1 次，剩余 X 次"。
- 额度为 0 时，"生成日程"按钮置灰或点击后给出明确说明，而不是点击后才转圈再报错。

### F4. 可理解的结果与下一步（对应 B3）

| 场景 | 前端表现 |
| --- | --- |
| 成功 | 展示日程 + toast"生成成功，剩余 X 次" |
| 额度不足 | toast"额度已用完"，说明"本次未调用模型、未扣额度"，给出下一步（当前无加额入口，见 §6） |
| 模型失败 | toast"生成失败，本次未扣额度，请删除含 [fail] 的任务后重试" |
| 并发多请求 | 多余请求在额度扣完后自动收到"额度不足"，用户不会看到负数 |

## 5. 非功能与约束

- 不改数据模型：`User.credits Int @default(3)` 保持不变，不加新表、不加加额字段。
- 不升级无关依赖，不引入队列/锁服务（单库行锁足够）。
- 所有提示文案为中文，面向非技术用户。

## 6. 明确不做（待办，交接时说明）

- 不做充值/订阅/加额入口——额度用完后用户暂时没有自助恢复路径，这是已知限制。
- 不做跨账号防刷与请求频控。
- 不做服务崩溃后"已预扣但模型结果未落库"的自动补偿（单服务场景概率低，按题目要求不做）。
