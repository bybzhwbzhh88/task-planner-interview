# 开发任务拆解与交接

本轮以“生成前阻止无效调用、成功扣费与结果一致、失败可恢复”为一个完整版本交付。以下是开发计划，不表示代码已实现；需求唯一来源为 [PRD](PRD.md)，验收编号见 [ACCEPTANCE](ACCEPTANCE.md)。

建议执行顺序：D1 → D2/D3 与 D5 并行 → D4/D6 → D7/D8。保持原 React/TypeScript/Wasp/Prisma/PostgreSQL 技术栈，不因额度需求升级无关依赖。

## 接口契约建议（开发评审后确认）

| 操作 | 请求/成功响应 | 失败语义 |
|---|---|---|
| 读取额度 | 无用户 ID 入参；返回 credits | 未登录、读取失败 |
| 读取日程 | 当前认证账号；结果编号、生成时间、内容，最近 20 份 | 未登录、读取失败 |
| 生成 | hours；返回已保存结果，包含编号与生成时间 | AUTH_REQUIRED、INVALID_INPUT、OUT_OF_CREDITS、GENERATION_BUSY、MODEL_FAILED、SAVE_FAILED |

推荐 HTTP 映射：401、400、402、409、502、500；具体以 Wasp 支持的错误机制为准。前端以稳定的业务错误原因处理，不靠匹配英文错误字符串。SAVE_FAILED 只有服务端确认回滚时才允许展示未扣费；网络异常和无法判定提交结果的异常统一归为结果未知。

## 优先级边界

D1–D8均为本题五条规则的闭环，不能只交付按钮提示而跳过服务端准入。范围内保留最小的最近日程核查；完整历史管理、搜索、分页、请求编号自动恢复、批量生成队列均延后。出现排期压力时先缩减这些后续增强，不削减扣费与保存一致性。

## 工程落点

- `src/demo-ai-app/operations.ts`：认证、准入、生成与查询入口。
- `src/client/App.tsx`：已有页头余额入口，与操作区统一数据来源或收敛展示位置。
- `src/demo-ai-app/DemoAppPage.tsx`：额度、按钮、结果、错误状态和历史展示。
- `src/demo-ai-app/demo-ai-app.wasp.ts`：按最终接口声明查询/动作。
- `src/demo-ai-app/mockAi.ts`：沿用模拟调用和 [fail] 行为，不替换成外部模型。
- `schema.prisma`：现有 User.credits 和 PlanResult 可覆盖核心范围；非必要不新增支付、预占或队列表。

## 工作量与风险

粗估 3–4 个工作日、约 5–7 人日，假设已有可运行环境及熟悉 Wasp 的前后端开发；不是招聘 48 小时提交要求的工期承诺。产品材料可先在题目时限内交付。正式排期需由开发确认框架、测试环境和人力。

上述估算拆分为：契约与评审0.5人日；服务端准入/事务/查询1.5–2人日；前端状态与历史1.5–2人日；集成测试/回归1.5–2.5人日。环境未就绪或错误契约调整会增加时间，不把区间当作承诺。

主要风险：错误码在客户端丢失导致误判、页面旧余额、保存失败未回滚、处理中异常未释放、网络断开被当成明确失败。每项均有验收案例，不以“按钮禁用”替代服务端并发验收。

## 发布门槛

1. 编译和类型检查通过；全部 P0 实际案例通过，附日志和数据库前后对比。
2. 无额度不调用、无透支、失败不扣费、保存与扣费一致，任一不满足均阻断发布。
3. 发布后关注拒绝、失败和提交日志；发现扣费错账优先暂停生成入口、保存证据并人工核查，不能通过批量猜测退款掩盖问题。
4. 不自动回退到原先不安全的额度逻辑。扩容多进程前重新评审并发控制。
