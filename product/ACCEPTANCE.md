# 验收案例与记录规范

本文件提供可执行的产品验收，不把演示原型当作真实系统。下面 AC01–AC13 的真实应用执行状态均为**待开发后执行**。已做的产品交付检查另见 [REVIEW.md](REVIEW.md)。

## 准备与证据口径

按 [README](../README.md) 启动应用，创建两个独立测试账号 A/B；用数据库 Studio 设置额度 0、1、3，确认没有生成进行中再设置，之后刷新页面。普通任务使用“整理面试资料”；明确模型失败使用含 [fail] 的任务。记录开始/结束时间、测试账号内部标识、前后余额、结果数量、接口结果与日志 callId；不记录真实个人联系方式。

一次 mock-ai.started 算一次模型调用。每次验证应隔离时间窗口，按 callId 配对，不把其他账号/其他用例日志混入。检查结果条数增量，不要求数据库里原本没有历史记录。

| ID / 需求 | 前置条件 | 操作 | 可观察预期 |
|---|---|---|---|
| AC01 / R1 | 新账号或 A 额度设 3 | 打开页面；模拟额度查询失败后恢复 | 正常显示 3 与每次成功扣 1；读取失败显示刷新入口，不显示假 0；刷新恢复 |
| AC02 / R2 | A 额度 0，有普通任务 | 页面点击检查；再绕过按钮直接发生成请求 | 按钮不可用且有原因；服务端拒绝，started=0、余额0、结果增量0；可查看历史 |
| AC03 / R4 | A 额度3，有普通任务 | 生成一次，刷新页面后查看历史 | started/succeeded 各1、余额2、结果增量1；成功提示，刷新后结果仍在 |
| AC04 / R4/R5 | A 额度1，任务含 [fail] | 生成失败；删除标记再生成 | 首次 started/failed 各1、余额1、结果增量0；提示未扣费且输入保留；第二次成功，余额0、结果增量1 |
| AC05 / R3 | A 额度1；使首个 mock 请求保持处理中 | 同时发送首个请求和9个重叠请求，全部落在处理中窗口 | 仅首个进入模型；9个忙碌拒绝且不排队；释放首个后成功，started=1、余额0、结果增量1；随后新请求额度不足 |
| AC06 / R3 | A 额度3；首个请求处理中 | 重叠提交第二个；首个完成后再主动生成 | 重叠请求忙碌拒绝，不消耗额外额度；第一轮余额2、结果增量1；新的主动请求成功后余额1、总结果增量2 |
| AC07 / R2/R3 | A 两标签均显示旧余额1 | 标签1生成完成；暂停标签2的焦点自动刷新，保留旧余额后直接请求 | 标签2服务端额度不足；总 started=1、余额0、结果增量1；标签2更新余额；不能依赖旧余额放行 |
| AC08 / R3 | A/B 各1额度，普通任务 | 第一轮在A处理中时发起B，确认两者均成功，各验证余额0、结果+1；将A重置额度1，添加[fail]后失败，再删标记重试 | B可进入模型，不被A全局阻塞；各自结果与余额隔离；A失败后可重新生成，不永久忙碌 |
| AC09 / R4 | A额度1，普通任务；测试环境注入保存失败 | 模型成功后使结果写入失败；再恢复写入重试 | 首次模型调用1次但结果增量0、余额1；确认事务回滚后提示未扣费；后续成功且处理权已释放 |
| AC10 / R6 | A有额度，普通任务 | 代理丢弃已提交成功请求的响应，恢复网络再刷新；另测请求未送达，以及请求已送达仍在处理时断网 | 三种情况下客户端均不宣称未扣费、不自动重试；已提交场景余额-1且历史+1；未送达场景调用0且余额不变；仍在处理时立即刷新不得宣称失败或完成，后续完成再核对；刷新本身不得新增模型调用 |
| AC11 / R2/R6 | 未登录；或登录A并已创建B历史 | 未登录请求；尝试在请求中伪造B用户ID查询/生成；提交无任务、越界小时数 | 未登录返回401且无调用；伪造B身份字段应被拒绝或忽略，绝不能读写B数据（若忽略，只按A身份继续正常校验）；无任务及0/25/1.25等非法时长拒绝、无调用或扣费 |
| AC12 / R1/R5/R6 | A有历史且有额度 | 快速连点；用键盘操作；模型成功后故意使余额/历史刷新失败 | 同页只发1次生成；生成中可感知且按钮不可重复激活；成功仍提示已保存已扣费，同时提示刷新失败；旧结果明确为已有日程 |
| AC13 / R5/R6 | A已生成过日程且仍有额度；新请求失败或结果未知 | 先成功生成，再添加[fail]生成失败；再删标记发请求并丢弃响应，期间编辑输入；最后刷新核查 | 旧结果明确标为“上次已保存日程”，不能冒充本次；编辑不更新余额或历史、不解除未知状态；核查后须主动确认再点击生成，新请求仍独立计费 |

## 并发验收的执行要求

“同时点击两个页面”只能做体验走查，不能单独证明无透支。开发需提供通过认证的并发脚本，或调用同一份真实服务逻辑的集成测试。推荐流程：

1. 初始化 A 额度1、普通任务，记录余额和结果数量；使用测试屏障让首个模型调用停留在处理中。
2. 发出首个请求，确认已进入模型；在释放屏障前，用 Promise.allSettled 等方式发出9个请求。
3. 确认9个请求均立即忙碌拒绝、started仍为1，再释放首个请求。
4. 验证最终余额0、结果新增1；继续主动请求应额度不足且不新增 started。
5. 重做额度3场景：忙碌拒绝不形成后台任务；首个完成后余额2，主动再次请求才生成下一份。

屏障只用于可重复验证，不修改正式 mock 的业务失败规则。没有屏障时必须用日志证明请求确实重叠；否则第二个请求在前一个完成后成功是合法行为，不能误判并发缺陷。

## 故障注入边界

AC09仅在测试库通过测试开关或可控的存储适配器故障令插入失败，不破坏真实数据表。AC10需用代理区分三个时点：请求未送达、服务端仍在处理、服务端已提交但响应丢失；不能用浏览器随机断网代替这三种精确定义。AC12的刷新失败仅拦截额度/历史查询响应，不拦截已成功返回的生成响应。测试必须保留原始成功结论。
