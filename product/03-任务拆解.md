# 03 任务拆解：日程生成的额度处理

## 判断、方案与状态

- **判断**：这个需求的风险不在“功能多”，而在“顺序和边界”——额度检查必须在调用前，扣减必须在成功后，并发必须防透支。任务拆解要按这个因果链排依赖，而不是按页面堆功能。
- **方案**：拆成四组——产品定义、后端规则、前端状态、验证交付。每组任务都标明交付物、完成标准、依赖和对应验收编号。
- **状态**：[产品侧任务已完成；开发任务为拆解建议，实际实现由技术方向按 SPEC 执行，完成后回写完成情况]。

> 规则见 01-需求与方案.md；流程与页面状态见 02-流程与原型.md；验收编号见 04-验收案例.md。

---

## 一、拆解原则

| 原则 | 说明 |
|---|---|
| 按因果链排依赖 | 先定规则，再定检查/扣减顺序，最后做并发和文案 |
| 每个任务有完成标准 | 不写“优化额度”，写“什么情况出现什么结果” |
| 任务对应验收 | 每条开发任务至少挂一个 AC 编号 |
| 范围外单列 | 明确不做的项，避免范围蔓延 |

## 四、后端任务的具体行为约束

| 任务 | 必须成立的行为 | 不做什么 |
|---|---|---|
| B1 | 额度 ≤ 0 时，在调用模型之前返回不足结果 | 不靠前端隐藏按钮来“保证”不调用 |
| B2 | 只有模型明确成功才扣 1；结果写入与扣减同一事务 | 不在调用前预扣 |
| B3 | 模型明确失败时额度不变，不写成功结果 | 不把失败当成功扣减后退款 |
| B4 | 并发下额度不为负，成功次数不超过可用额度 | 不依赖“用户不会双击” |
| B5 | 脚本可重复跑，输出成功次数和最终额度 | 不写只能手工点一次的验证 |

> 具体用事务、条件更新还是其他方式，由技术方向在 `SPEC.md` 说明；本表只约束行为结果。
